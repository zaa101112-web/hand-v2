1 문서 목적과 개발 범위

1.1 문서 목적

본 문서는 손동작 기반 비접촉 컴퓨터 제어 프로그램의 아키텍처와 동작 규칙을 정의한다. 팀원들이 손 인식, 화면 인터페이스, 컴퓨터 제어 및 화면 캡처 기능을 병행 개발할 수 있도록 모듈별 책임과 연결 기준을 통일하는 것을 목적으로 한다.

프로그램은 웹캠으로 입력받은 영상에서 손의 위치와 움직임을 분석하고, 인식된 동작을 현재 모드에 맞는 명령으로 변환한다. 동일한 손동작이 모드에 따라 다른 기능으로 연결되므로, 제스처 인식 결과와 실제 명령 실행을 구분하고 공통 규칙에 따라 처리한다.

본 문서에서 정의할 사항은 다음과 같다.

  • 시스템 구조와 역할 분담: 모듈별 책임과 처리 순서를 정의한다.
  • 데이터 전달 규격: 손 좌표, 제스처 이벤트, 실행 명령 및 처리 결과의 형식을 통일한다.
  • 제스처 판정과 실행 조건: 동작의 시작·유지·종료 조건, 유지 시간, 재실행 조건을 정의한다.
  • 모드와 충돌 처리: 모드별 허용 명령, 조작 활성화 여부, 동시 인식 시 우선순위와 중복 실행 방지 규칙을 정의한다.
  • 오류 처리와 검증 기준: 손 추적 유실, 입력 장치 오류, 명령 실행 실패 등의 처리 방법과 기능별 테스트 기준을 정의한다.

팀원들은 본 문서의 공통 규격을 기준으로 담당 기능을 구현한다. 다른 모듈에 영향을 주는 데이터 형식이나 동작 규칙을 변경할 때에는 관련 담당자와 합의하고 문서에도 변경 내용을 반영한다. 실험을 통해 조정하는 인식 임계값과 시간 기준은 초기 설정값과 최종 검증값을 구분하여 관리한다.

1.2 시스템 개발 범위

본 프로젝트는 사용자 PC에서 실행되는 Python 기반 데스크톱 프로그램으로 개발한다. 웹캠 영상 처리와 손동작 분석은 로컬 환경에서 수행하며, 별도의 유료 API나 클라우드 서버를 사용하지 않는다.

주요 개발 범위는 다음과 같다.

구분 개발 범위
실시간 손 인식 웹캠 영상에서 최대 양손의 관절 좌표를 추출하고 손의 위치와 움직임을 추적한다.
제스처 분석 브이 활성화, 숫자 3 중단, 집기, 좌우 쓸기, 검지 가리키기, 주먹 후 펼치기, 양손 거리 변화 등을 판정한다.

실제 마우스 제어 손동작으로 운영체제 커서를 이동하고 드래그를 수행한다. 필수 구현 기능으로 포함한다.
공통 상태 관리 현재 모드, 조작 활성화 여부, 진행 중인 동작을 관리하고 명령 충돌과 중복 실행을 방지한다.
상태 표시 현재 모드, 인식한 동작, 조작 활성화 여부와 주요 오류를 화면에 표시한다.

제스처별 최종 손 모양과 판정 기준은 인식 실험 결과에 따라 조정할 수 있다. 변경 시에는 해당 제스처를 사용하는 모드와 기능에 미치는 영향을 함께 확인한다.

1.3 실행 환경과 지원 범위

최종 실행 및 검증 환경은 Windows 11과 단일 모니터로 설정한다. 브라우저 제어는 Windows용 Google Chrome을 대상으로 하며, Chrome 창이 활성화된 상태에서만 브라우저 명령을 실행하도록 한다.

코드 작성과 손 인식 로직 개발은 macOS와 Windows에서 진행할 수 있다. 다만 운영체제의 영향을 받는 키보드 입력, 실제 마우스 제어, 화면 캡처 및 실행 파일 배포는 Windows 환경에서 최종 검증한다.

주요 구현 도구는 다음과 같다.

Python과 주요 라이브러리의 버전은 초기 실행 검증 후 팀 공통 버전으로 확정하고, 의존성은 requirements.txt로 관리한다. Windows 화면 배율에 따라 표시 좌표와 캡처 좌표가 달라질 수 있으므로, 최종 검증 시 화면 배율 설정과 좌표 일치 여부를 함께 기록한다.

1.4 기능 간 경계

자체 프로그램 내부의 화면 조작과 운영체제에 전달하는 입력은 구분하여 구현한다.

이미지·발표 모드의 이미지 선택·이동, 확대·축소 및 화면 전환은 PySide6 프로그램 내부에서 처리한다. 발표 포인터도 프로그램에서 표시하는 것을 기본으로 한다. 실제 마우스 커서 이동과 드래그는 필수 기능으로 구현하며, 모드별 실행 조건을 정의한 후 PyAutoGUI를 통해 처리한다.

브라우저 모드에서는 인식된 제스처를 Chrome 단축키 명령으로 변환한다. 캡처 모드에서는 선택 영역 조절과 확정·취소에 필요한 명령만 처리한다. 하나의 손동작이 여러 모드의 명령을 동시에 실행하지 않도록 현재 모드를 기준으로 명령을 분배한다.

1.5 초기 개발 제외 범위와 완료 기준

초기 개발에서는 다중 모니터, Chrome 이외의 브라우저, macOS에서의 전체 기능 동작 보장, 외부 발표 프로그램의 직접 제어를 지원 범위에 포함하지 않는다. 자체 손 인식 모델 학습과 클라우드 기반 영상 처리도 초기 범위에서 제외한다. 추가 지원이 필요한 경우 기본 기능의 구현과 검증을 마친 뒤 팀 협의를 통해 범위를 확장한다.

프로젝트의 기본 완료 조건은 최종 Windows 환경에서 손 인식부터 명령 실행까지 전체 흐름이 연결되고, 세 가지 모드의 주요 기능을 시연할 수 있는 상태로 설정한다. 또한 모드 간 명령 충돌, 의도하지 않은 반복 실행, 손 추적 유실 시의 조작 종료 여부를 확인한다. 기능별 성공률과 반응 시간 등 정량적인 통과 기준은 테스트 및 완료 기준 항목에서 별도로 정의한다.

2 전체 시스템 아키텍처

2.1 설계 목적과 기본 원칙

시스템은 하나의 Python 데스크톱 프로그램 안에서 영상 입력, 손 추적, 특징 계산·제스처 인식, 공통 제어, 화면 인터페이스, 컴퓨터 제어, 캡처 저장 모듈로 구성한다. 각 모듈은 담당 기능을 수행하고, 정해진 형식의 데이터와 이벤트를 통해 연결한다.

손동작을 인식하는 과정과 실제 기능을 실행하는 과정을 분리한다. 인식 모듈은 사용자의 손 상태와 제스처를 전달하며, 공통 제어 모듈은 현재 모드와 조작 상태를 확인하여 실행할 명령을 결정한다. 화면 인터페이스, 컴퓨터 제어 및 캡처 저장 모듈은 전달받은 명령을 실행하고 결과를 보고한다.

설계 및 동작 규칙 담당자는 모듈의 책임, 연결 규격과 실행 조건을 정의한다. 제어 담당 팀원은 이 명세에 따라 공통 제어·상태 관리와 컴퓨터 제어 코드를 구현한다. 별도의 역할 분담 절은 생략하고 본 항목의 책임 구분을 사용한다.

다음 원칙을 공통으로 적용한다.

  • 제스처 인식 모듈에서 UI 변경, 단축키 입력 또는 마우스 조작을 직접 실행하지 않는다.
  • 모드와 조작 활성 상태의 변경은 공통 제어 모듈을 통해 처리한다.
  • 자체 UI 객체 이동과 실제 마우스 드래그는 서로 다른 실행 명령으로 구분한다.
  • 일반 조작은 활성 상태에서만 허용하되, 중단과 오류 처리를 위한 입력 해제는 대기 상태에서도 수행할 수 있다.
  • 시간과 거리 등의 인식 기준은 설정값으로 관리하며, 세부 값은 실험을 통해 확정한다.

2.4 실행 구조와 모듈 연결 방식

상시 실행 구조는 메인·인식·입력 실행·캡처 실행의 4개 스레드로 고정한다. 기능 패키지마다 임의로 스레드를 추가하지 않는다. 이미지 디코딩은 별도의 QThreadPool 단기 작업을 사용하므로 전체 OS 스레드 수가 항상 4개라는 뜻은 아니다.

인식 작업 스레드 웹캠 프레임 획득, 손 추적, 특징 계산, 제스처 인식

입력·캡처 실행 스레드는 app.py가 생성·관리한다. 시간이 걸리는 대기나 파일 저장으로 메인 스레드를 막지 않도록 한다. 마우스와 키보드 입력은 컴퓨터 제어 모듈에서 순서대로 처리하여 서로 다른 작업이 입력 순서를 뒤섞지 않도록 한다.

인식 결과와 명령, 처리 결과는 PySide6의 Signal/Slot을 통해 전달한다. 작업 스레드는 UI 위젯을 직접 수정하지 않는다. 공통 상태의 변경은 메인 스레드의 공통 제어 모듈에서 처리하며, 인식 모듈에 필요한 설정이나 상태는 메시지로 전달한다.

연속적인 커서 좌표와 영역 좌표는 최신 값을 우선 처리하고, 이전 좌표가 무제한으로 쌓이지 않도록 한다. 집기 시작·종료, 활성화·중단, 캡처 확정 등 상태를 바꾸는 이벤트는 발생 순서를 보존한다. 모드 변경이나 중단 전에 생성된 일반 조작 이벤트가 이후에 실행되지 않도록 상태 변경 시 기존 작업을 무효화한다. 중단 및 입력 해제 요청은 일반 조작보다 우선 처리한다.

프로그램 시작 시 조작 상태는 대기로 설정한다. 기본 모드는 IMAGE이며, 모드 선택 버튼을 통한 전환 규칙은 5번에서 정의한다. UI는 공통 상태를 받아 표시하며, 상태를 임의로 변경하지 않는다.

모드가 바뀌면 기존 모드의 진행 중 조작을 종료하고, 관련 제스처 이력과 대기 중인 일반 명령을 초기화한다. 실행 모듈에서 오류가 발생하면 공통 제어 모듈이 이를 받아 필요한 조작 종료와 사용자 안내를 결정한다.

손 개수가 두 개에서 하나 또는 영 개로 바뀌어도 프로그램 활성 상태는 유지한다. 추적 유실 시에는 해당 손이 참여한 조작만 종료하며, 양손 조작 종료 후 남은 손은 새로운 한 손 동작을 시작할 수 있다. 실제 드래그 담당 손을 잃으면 해당 버튼을 해제한다.

2.6 브이 활성화와 숫자 3 중단 구조

본 문서에서 인식 중단은 카메라나 손 추적을 종료하는 것이 아니라, 일반 조작 명령의 실행을 중단하는 것을 의미한다. 대기 상태에서도 브이 동작을 감지하기 위한 영상 입력과 손 추적은 유지한다.

대기 상태에서 숫자 3을 보여도 상태는 유지된다. 활성 상태에서는 브이를 활성화 명령으로 다시 처리하지 않는다. 활성화에 사용한 브이가 브라우저의 두 손가락 쓸기 등으로 바로 이어지지 않도록, 활성화 동작이 해제된 뒤 새로운 일반 동작을 판정한다.

숫자 3 중단 명령은 모든 모드에서 일반 조작보다 우선한다. 중단이 확정되면 새로운 일반 명령을 차단하고, 대기 중인 일반 명령을 무효화하며, 프로그램이 누른 마우스 버튼과 키를 해제한다. UI 객체 이동과 영역 조절 등도 종료한다. 캡처 선택 중 중단은 저장 없이 취소하고 이전 모드의 대기 상태로 복귀한다. 이미 시작된 저장 작업은 5.9의 규칙으로 처리하며, 중단 자체가 새 저장을 발생시키지 않는다.

기존 제안서의 손바닥 유지에 의한 활성·일시정지 전환은 적용하지 않으며, 브이 활성화와 숫자 3 중단으로 대체한다.

2.7 실제 커서와 드래그 처리 구조

실제 운영체제 커서 이동과 드래그는 필수 구현 기능으로 포함한다. 자체 UI의 객체 이동과 실제 마우스 입력은 다음과 같이 분리한다.

조작 대상 실행 모듈 처리 방식
자체 이미지 객체 화면 인터페이스 UI 객체의 위치와 표시 상태 변경
자체 발표 포인터 화면 인터페이스 화면 내 포인터 위치 변경
실제 운영체제 커서 컴퓨터 제어 화면 좌표로 변환된 위치에 마우스 이동
실제 운영체제 드래그 컴퓨터 제어 버튼 누름, 이동, 버튼 해제를 순서대로 실행
캡처 선택 영역 화면 인터페이스 선택 사각형의 위치와 크기 갱신

공통 제어 모듈은 현재 모드와 조작 대상에 따라 하나의 실행 경로를 선택한다. 동일한 집기 이벤트가 UI 객체 이동과 실제 마우스 드래그를 동시에 시작해서는 안 된다. 공통 마우스는 손바닥 중심 이동과 검지 접기·펴기로 제어하며, 모드별 허용 범위는 5.3에서 정의한다.

실제 드래그는 시작·유지·종료 단계를 구분하여 처리한다. 버튼 누름은 시작 시 한 번, 버튼 해제는 종료 시 한 번 수행하며, 유지 중에는 위치를 갱신한다. 중단, 모드 변경, 조작에 필요한 손의 추적 유실, 프로그램 종료 또는 실행 오류가 발생하면 진행 중인 드래그를 종료하고 입력 해제를 수행한다. 추적 유실을 확정하는 시간 기준은 후속 안정화 규칙에서 정의한다.

인식 모듈은 카메라 기준 좌표를 전달한다. 공통 제어 측 좌표 변환 계층은 대상에 맞는 UI 좌표 또는 실제 화면 픽셀 좌표로 변환한다. 좌우 반전, 화면 배율, 화면 경계 제한의 기준은 후속 좌표 규칙에서 통일하여 실행 모듈에서 중복 변환하지 않도록 한다.

2.8 캡처 모듈 연결 구조

캡처는 영역 선택과 실제 촬영·저장을 분리한다. 화면 인터페이스는 선택 영역을 표시하고, 캡처 저장 모듈은 최종 영역을 촬영하여 저장한다. 두 모듈 사이의 순서는 공통 제어 모듈에서 관리한다.

캡처 진입 요청
→ 현재 조작 종료 및 이전 모드 기록
→ 캡처 선택 화면 표시
→ 손동작에 따른 영역 갱신
→ 확정 요청 및 영역 유효성 검사
→ 선택 화면 숨김 요청
→ 숨김 및 화면 반영 완료 확인
→ 실제 픽셀 기준 영역 촬영 및 저장
→ 결과 표시 및 이전 모드 복귀

선택 화면을 숨기라는 요청을 보낸 직후 촬영하지 않고, 캡처에 오버레이가 포함되지 않도록 숨김과 화면 반영을 확인한 뒤 촬영한다. 실패 시에는 성공으로 표시하지 않고 오류를 전달한다. 캡처 진입·저장·취소 및 재시도 정책은 5.6부터 5.9에서 정의한다.

2.9 시작과 종료 및 후속 명세

프로그램 시작 시 공통 상태와 실행 모듈을 초기화한 뒤 영상 입력 및 손 추적을 시작하고, UI에 대기 상태를 표시한다. 웹캠이나 모델 준비에 실패하면 일반 조작을 허용하지 않고 오류를 안내한다.

프로그램 종료 시에는 일반 명령 접수를 중단하고, 진행 중 조작 취소와 입력 해제를 우선 수행한다. 이후 작업 스레드와 실행 작업을 정리하고 카메라 등 자원을 해제한다. 종료 도중 이전 명령이 새로 실행되지 않도록 한다.

본 항목은 모듈 구성, 실행 위치, 상태 소유권과 명령 전달 경로를 정의한다. 구체적인 데이터 필드, 모드별 제스처 매핑, 인식 임계값, 모드 전환 방법, 캡처 세부 동작과 테스트 통과 기준은 후속 항목에서 확정한다.

4.1 목적과 공통 표현

본 항목은 팀원별 구현을 연결하기 위한 공통 데이터 계약을 정의한다. 별도 역할 분담 절인 3번은 생략하고, 2번의 책임 구분을 사용한다. 아래 필드명과 자료형을 공통 규격으로 사용하며, 변경 시 송신·수신 모듈을 함께 수정한다.

Python 내부 메시지는 dataclass, 종류와 상태는 Enum으로 정의한다. 이 문서의 예시는 가독성을 위한 JSON 표현이며, 실제 Signal/Slot 전달에 JSON 직렬화를 요구하지 않는다. 송신 이후에는 메시지와 내부 목록을 변경하지 않으며, 수신 측도 받은 메시지를 직접 수정하지 않는다.

공통 규칙 정의

손 개수는 활성·대기 상태를 결정하지 않는다. 현재 보이는 손과 특정 조작에 참여하는 손을 별도로 표현한다. 손이 줄어들면 필요한 손을 잃은 조작만 종료하고, 프로그램 활성 상태는 유지한다.

4.2 좌표 및 시간 기준

좌표에는 반드시 좌표계를 함께 전달한다. 다음 좌표 방향과 반전 방식은 구현을 위한 설계 기본안으로 사용하며, 통합 전 변경할 경우 모든 관련 모듈에 동시에 반영한다.

좌표계 식별값 단위와 기준
카메라 CAMERA_NORMALIZED 반전하지 않은 입력 영상의 좌측 상단 원점, 오른쪽 +x, 아래쪽 +y. 영상 내부 x·y는 0~1
자체 UI UI_LOGICAL 지정 위젯의 좌측 상단 원점, 논리 좌표 단위
화면 SCREEN_PIXEL 대상 단일 모니터의 좌측 상단 원점, 실제 픽셀 단위

미리보기는 좌우 반전하고, 사용자 손의 이동 방향과 화면 조작 방향을 맞추기 위한 x축 반전은 공통 좌표 변환 계층에서 한 번 적용한다. 실행 모듈은 이미 변환된 값을 다시 반전하지 않는다. 화면 배율 보정도 같은 계층에서 수행한다.

관절의 z는 추적기가 반환한 상대 깊이 값으로 유지하며 실제 거리나 0~1 범위로 해석하지 않는다. 영상 밖 관절의 x·y 값이 범위를 벗어나면 원본을 보존하고, 유효성 판단과 실행 좌표의 화면 경계 제한을 구분하여 처리한다.

공통 자료형 필드
Landmark x: float, y: float, z: float
Point2D x: float, y: float, space: CoordinateSpace, target_id: str
CaptureRect left: int, top: int, width: int, height: int, space: SCREEN_PIXEL, target_id: str

카메라 target_id는 camera_0, UI는 대상 위젯 ID, 화면은 monitor_0처럼 명시한다. 캡처 사각형은 왼쪽·위쪽을 포함하고 오른쪽·아래쪽 경계는 제외한다. width와 height는 양수여야 하며 화면 내부로 제한한 최종 영역을 전달한다. UI 영역은 픽셀로 변환한 뒤 CaptureRect로 생성한다.

촬영 시각과 이벤트 생성 시각은 구분한다. 처리 지연과 이벤트 순서는 벽시계 날짜가 아닌 공통 단조 증가 시각을 사용한다.

4.3 손 추적 데이터

손 추적 모듈은 프레임마다 TrackingFrame을 전달한다. 정상적으로 영상을 읽었으나 손을 찾지 못한 경우에도 빈 손 목록을 전달한다.

TrackingFrame 필드 자료형 의미
schema_version int 규격 버전
frame_id int 처리 프레임 번호, 증가 순서 유지
captured_at_ms int 영상 획득 시각
camera_id str 영상 장치 식별자
image_width int 원본 프레임 너비
image_height int 원본 프레임 높이
hands list[HandData] 현재 유효하게 추적되는 손 0~2개
HandData 필드 자료형 의미
hand_id str 추적 구간 동안 유지하는 손 식별자
handedness LEFT / RIGHT / UNKNOWN 사용자 실제 좌우 손으로 보정한 분류, 손 ID와 별개
raw_handedness LEFT / RIGHT / UNKNOWN 또는 None 선택 진단 필드. 모델의 보정 전 라벨
handedness_score float 또는 None 선택. 좌우 분류 점수이며 제스처 신뢰도로 사용하지 않음

handedness 보정은 7.7의 검증된 설정으로 추적 모듈에서 한 번 수행한다. 화면 반전과 라벨 교환을 혼동하지 않는다. 검증되지 않은 설정에서는 handedness를 UNKNOWN으로 내보내고 raw_handedness를 진단에 사용한다.

hand_id는 검출 목록 순서나 handedness 자체로 만들지 않고 추적 계층에서 프레임 사이 대응 관계를 관리하여 부여한다. 대응을 확신할 수 없거나 유실이 확정된 뒤 재검출된 손에는 새 ID를 부여한다. 다른 손이 기존 조작을 자동으로 이어받지 않는다. 잠깐의 검출 누락을 유실로 확정하는 시간 기준은 후속 안정화 규칙에서 정의한다.

카메라 읽기 실패는 hands=[]로 숨기지 않고 별도 SystemEvent로 보고한다. 추적 유실 유예 중에도 보이지 않는 손의 오래된 좌표로 새 이동 명령을 생성하지 않는다.

4.4 제스처 이벤트

제스처 인식 모듈은 원래 손 모양과 움직임에 해당하는 GestureEvent를 전달한다. 브라우저 단축키 등 모드별 실행 명령은 이 단계에서 생성하지 않는다.

GestureEvent 필드 자료형 의미
schema_version int 규격 버전
event_id str 이벤트 식별자
frame_id int 판정에 사용한 최신 프레임
captured_at_ms int 해당 프레임 획득 시각
emitted_at_ms int 이벤트 생성 시각
context_version int 인식 시 적용한 공통 제어 맥락 버전
gesture_type GestureType 동작 종류
phase TRIGGER / START / UPDATE / END / CANCEL 이벤트 단계
interaction_id str 또는 None 연속 동작이면 필수, 단발 동작이면 None
participant_hand_ids list[str] 이 동작에 참여한 손 1개 또는 2개
payload 종류별 dataclass 좌표·방향·거리 등 부가 값
reason CancelReason 또는 None CANCEL이면 필수. 전체 목록은 부록 A.1

GestureType의 전체 목록은 부록 A.2를 기준으로 한다. 아래 표와 5.11은 각 이벤트의 단계·payload를 설명한다.

이벤트 단계 payload의 필수 내용
V_SIGN, THREE_SIGN TRIGGER 빈 데이터. 손 ID는 participant_hand_ids에 기록
POINT, PINCH START, UPDATE position: Point2D
TWO_HAND_PINCH START, UPDATE points: 손 ID별 Point2D 목록, distance: float, scale_ratio: float
SWIPE TRIGGER direction: LEFT/RIGHT, direction_space: CAMERA_NORMALIZED, finger_count: int. 원본 영상 x 증가가 RIGHT
FIST_OPEN, CIRCLE, THUMBS_UP TRIGGER 빈 데이터. 추가 판정 정보는 추후 규격으로 확장
연속 동작 종료 END, CANCEL 빈 데이터 허용. CANCEL에는 reason 필수

양손 distance는 정규화 좌표에 영상 너비·높이를 곱한 영상 평면에서 계산한 두 집기점 사이의 픽셀 거리이며, scale_ratio는 시작 시 거리 대비 현재 거리의 비율이다. 기준 거리가 유효한 양수일 때만 시작한다. points의 각 항목은 hand_id와 position을 포함해 목록 순서에 의존하지 않는다.

START 이후 UPDATE를 여러 번 전달하고, 정상 해제 시 END, 추적 유실 등 비정상 종료 시 CANCEL을 한 번 전달한다. 한 interaction_id가 끝난 뒤에는 UPDATE를 다시 보내지 않는다. 재시작에는 새로운 interaction_id를 사용한다. 단발 동작은 조건 충족 시 TRIGGER를 한 번 보내고, 재실행 조건 충족 전까지 반복 발행하지 않는다.

4.5 한 손과 양손 조작의 참여 관계

현재 감지된 손 목록은 TrackingFrame.hands, 특정 동작의 참여 손은 GestureEvent.participant_hand_ids로 구분한다. 최대 두 손을 추적하되 한 손 동작에는 실제 참여한 손 하나만 기록한다.

상황 데이터 및 제어 처리
한 손 조작 중 반대 손 등장·유실 해당 조작의 참여 손 ID 유지, 동작에 영향 없음
두 손이 보여도 한 손 동작 수행 참여 손 하나를 전달하고 해당 동작 실행
양손 동작의 참여 손 유실 확정 해당 interaction_id를 CANCEL, 마지막 적용 결과 유지
양손 동작 종료 후 한 손 동작 시작 새 시작 조건 확인 후 새로운 interaction_id 생성
드래그 참여 손 유실 확정 해당 드래그 취소 및 버튼 해제
모든 손 유실 진행 중인 손 조작 종료, activation은 ACTIVE 유지
숫자 3 판정 완료 전체 일반 조작 종료, activation을 WAITING으로 변경

양손 조작이 끝난 자세를 한 손 조작의 시작으로 자동 변환하지 않는다. 동작별 재시작 조건은 후속 규칙에서 정한다. 커서 제어권은 확정된 시작 조건을 만족하여 공통 제어가 승인한 손에 부여하고, 다른 손이 나타났다는 이유로 넘기지 않는다. 동시에 두 손이 시작 조건을 만족할 때의 선택 기준은 후속 충돌 규칙에서 정의한다.

4.8 공통 상태와 UI 요청

공통 제어 모듈만 AppState를 변경한다. UI 및 인식 모듈은 필요한 상태 사본을 전달받는다.

AppState의 전체 필드·자료형·기본값·소유권은 부록 A.5만을 기준으로 한다. 이 절에서는 상태 변경과 전달 원칙을 설명한다.

InteractionState에는 interaction_id, action_type, participant_hand_ids, target_id를 포함한다. 여러 조작의 동시 허용 여부는 충돌 규칙으로 결정하며, 목록 자료형 자체가 동시 실행을 허가하지는 않는다. 실제 눌린 키·버튼 상태는 컴퓨터 제어 모듈이 관리·보고하고 공통 제어는 해제 완료 여부를 확인한다.

UI 요청은 UIRequest로 전달하며 schema_version, request_id, emitted_at_ms, request_type, payload를 포함한다. request_type의 전체 목록은 부록 A.4를 기준으로 하며, 캡처 선택 화면 숨김 완료는 capture_request_id를 포함한 별도 완료 알림으로 전달한다. 숨김 알림을 받은 뒤 화면 반영을 확인하고 SAVE_CAPTURE를 발행한다.

4.9 순서와 무효화 규칙

인식 모듈은 공통 제어가 전달한 context_version을 적용하고 이벤트에 기록한다. 새 맥락을 적용할 때 이전 제스처 이력을 정리한다. 공통 제어는 현재 맥락과 다른 일반 이벤트를 폐기한다. 촬영 시각이 마지막 맥락 변경보다 오래된 프레임에서 생성된 일반 이벤트도 실행하지 않는다.

손 개수 변경이나 단일 조작 종료만으로 전체 context_version을 올리지 않는다. 해당 interaction_id만 종료하여 무관한 조작이 영향을 받지 않도록 한다. 전체 중단과 모드 변경에서는 맥락을 갱신하고 진행 중 조작을 정리한다.

실행 모듈은 대기 중인 일반 명령에 대해 실행 직전 맥락 유효성을 검사한다. 새 맥락과 입력 해제는 일반 명령보다 우선 전달·적용한다. RELEASE_ALL_INPUTS 같은 정리 명령은 과거 맥락이라는 이유로 버리지 않는다. 이미 끝난 명령은 소급 취소할 수 없으므로 결과를 기록하되 과거 결과가 현재 모드를 되돌리거나 새 조작을 시작하게 하지 않는다.

연속 UPDATE는 같은 interaction_id 안에서 최신 값으로 병합할 수 있다. START, END, CANCEL, TRIGGER는 병합하지 않는다. 대체된 절대 좌표 UPDATE 명령은 SUPERSEDED 취소 결과로 처리한다. 상대 변화량인 스크롤은 최신 값만 남기지 않고 누적 합으로 병합한다. 일반 종료 시에는 마지막 유효 UPDATE 뒤에 END를 처리하며, 강제 중단 시에는 남은 UPDATE를 버리고 즉시 입력 해제를 수행한다.

4.11 UI 요청과 완료 보고

전체 요청 목록은 부록 A.4가 기준이다. 아래 표는 기본 요청 처리의 설명이며 대화상자 요청의 동작은 5.13을 참조한다. UIRequest는 사용자 의도를 전달하고 ExecutionCommand는 실제 작업을 지시한다. Enum은 각각 UIRequestType과 CommandType으로 분리하며 UI 요청은 모두 REQUEST_ 접두사를 사용한다. 기존 무접두사 UI 종류는 2.0에서 폐기한다.

REQUEST_ENTER_CAPTURE 빈 데이터 캡처 외 상태. 기존 activation 보존

물리 Esc와 UI 중단 버튼은 REQUEST_STOP으로 통일한다. 제스처 숫자 3은 GestureEvent를 통해 들어오지만 같은 중단 처리 함수를 사용한다. 각 요청은 request_id로 중복 제거하고 UIRequestResult를 반환한다.

UIRequestResult 필드는 schema_version: int, request_id: str, status: ACCEPTED/REJECTED/COMPLETED/FAILED/CANCELLED, emitted_at_ms: int, error_code: ErrorCode 또는 None, message: str 또는 None이다. ACCEPTED는 요청 수락일 뿐 작업 성공이 아니다. 저장 요청은 실제 저장 결과까지 기다려 최종 상태를 반환하고, 여러 실행 명령은 공통 제어의 요청→명령 ID 맵으로 연결한다. 단순 상태 변경은 COMPLETED를 바로 반환할 수 있다. 종료 완료 결과는 UI 종료 직전 최선의 방식으로 전달한다.

저장 경로 요청은 절대 경로인지 검증한 뒤 폴더 생성·쓰기 권한을 확인하고 사용자 설정 저장이 성공한 경우에만 반영한다. 실패 시 기존 경로를 유지한다. UI가 파일 대화상자를 취소하면 요청 자체를 보내지 않는다. camera 재연결은 CameraReconnectRequest(schema_version, request_id)로 VisionWorker.reconnect에 전달하고 CameraReconnectResult(schema_version, request_id, success, error_code, message)로 완료를 보고한다. 재연결 후 WAITING을 유지한다.

4.12 안내와 입력 상태 보고

일반 안내는 last_error에 넣지 않고 UserNotice로 전달한다. 필드는 schema_version: int, notice_id: str, code: NoticeCode, message: str, severity: INFO/WARNING/ERROR, duration_ms: int, related_request_id: str 또는 None, details: 종류별 payload 또는 None이다. duration_ms=0은 사용자 확인 전까지 유지하며 일반 안내 기본값은 3000ms, 저장 성공은 5000ms다. 동일 code와 관련 요청의 반복 안내는 2초 이내에는 하나로 갱신한다.

NoticeCode와 details의 전체 목록은 부록 A.7을 따른다. 괄호 필드는 details의 자료형을 뜻한다. 오류 결과도 사용자에게 표시할 때 UserNotice를 생성할 수 있으나 오류 상태 자체는 last_error에 유지한다. 저장 성공 안내와 경로는 실제 ExecutionResult.SUCCESS 이후에만 생성한다.

InputState의 유일한 작성자는 ComputerExecutor다. 필드는 schema_version: int, revision: int, observed_at_ms: int, held_buttons: tuple[MouseButton,...], held_keys: tuple[str,...], release_status: IDLE/PENDING/CONFIRMED/FAILED, related_request_id: str 또는 None이다. 이 상태는 프로그램이 성공적으로 전송한 입력에 대한 추적 기록이며 물리 키보드 전체 상태나 OS의 절대적 진실로 표현하지 않는다.

누름·해제 성공 또는 실패, 해제 요청 접수 때마다 새 revision으로 보고한다. Controller는 최신 사본만 AppState.input_state에 저장하고 실제 버튼 집합을 직접 수정하지 않는다. 입력 해제 요청을 보낸 시점에는 공통 제어의 release_pending을 참으로 두고, 대응 결과 성공과 해당 InputState의 CONFIRMED 및 빈 버튼·키 목록을 확인한 뒤 해제 완료로 판단한다. 해제 실패·응답 부재 시 일반 입력 재개를 차단한다. 초기 보고 전 AppState.input_state는 None이며 입력 상태를 확인할 때까지 실제 제어를 시작하지 않는다.

SHUTDOWN_TIMEOUT 전체 종료 10초 초과, 비정상 종료 경로

SystemEventCode는 DISPLAY_CHANGED, CAMERA_DISCONNECTED, MODULE_ERROR를 사용한다. SystemEvent에는 기존 필드에 error_code: ErrorCode 또는 None을 추가한다. DISPLAY_CHANGED는 정상 환경 변경 알림이며 그 자체를 오류로 표시하지 않는다. payload로 monitor_id, width_px, height_px, scale_x, scale_y를 전달하고 좌표 조작 정리·재초기화를 수행한다. 실패한 경우에만 MODULE_ERROR와 DISPLAY_REINIT_FAILED를 보고한다. MODULE_ERROR에는 error_code가 필수다. 기존 code는 SystemEventCode를 의미하도록 통일한다.

5 모드와 상태 전환 규칙

5.1 상태 구분과 시작 상태

프로그램의 작업 모드와 조작 활성 상태는 독립적으로 관리한다. 작업 모드는 IMAGE, BROWSER, CAPTURE이며, 조작 상태는 WAITING과 ACTIVE이다. 프로그램 실행 시 IMAGE + WAITING으로 시작한다. 카메라와 손 추적 준비가 끝나면 브이 활성화 동작을 감지한다.

WAITING에서는 손동작에 의한 커서 이동·클릭·드래그·스크롤과 일반 기능 실행을 차단한다. 카메라와 손 추적은 유지한다. 물리 마우스를 통한 프로그램 버튼 조작은 허용한다. ACTIVE에서는 현재 모드에 허용된 동작을 실행한다.

감지되는 손의 개수가 바뀌어도 activation은 변경하지 않는다. 필요한 손을 잃은 개별 조작만 종료하며, 손이 다시 나타났을 때 새 동작의 시작 조건을 만족하면 사용할 수 있다.

5.2 활성화와 전체 중단

현재 상태 입력 다음 상태 및 처리
WAITING 브이 유지 판정 완료 ACTIVE로 전환, 브이 해제 대기
ACTIVE, 브이 해제 대기 활성화에 사용한 브이 해제 확인 일반 동작 허용
ACTIVE 숫자 3 판정 완료 일반 조작 취소, 입력 해제, WAITING으로 전환
WAITING 숫자 3 상태 유지
ACTIVE 손 개수 감소 또는 모든 손 유실 해당 조작 종료, ACTIVE 유지

브이는 검지·중지를 펼치고 나머지 손가락을 접는 동작이다. 숫자 3은 엄지·검지·중지를 펼치고 약지·소지를 접는 동작이다. 어느 손으로도 활성화·중단을 요청할 수 있다. 활성 상태의 브이는 활성화 명령으로 재해석하지 않고, 두 손가락 동작의 시작 자세로 사용할 수 있다.

숫자 3은 일반 조작보다 우선한다. 같은 처리 구간에서 중단과 일반 명령이 함께 판정되면 중단을 적용하고 일반 명령을 폐기한다. 중단 시 실제 드래그를 해제하고, UI 이동과 양손 조작도 종료한다. 중단 때문에 새 클릭, 캡처 저장 또는 다른 일반 기능을 발행하지 않는다. 단, 운영체제에서 이미 눌린 버튼을 해제하는 효과까지 되돌릴 수 있는 것은 아니다.

5.3 공통 마우스 조작

활성 상태에서는 IMAGE와 BROWSER 모두 실제 커서로 프로그램의 모드 버튼을 선택할 수 있다. CAPTURE에서는 커서와 왼쪽 클릭을 선택 화면의 저장·취소 등 UI 조작에 사용한다. 캡처 선택 화면은 입력을 받아 뒤쪽 프로그램으로 클릭이 전달되지 않도록 한다.

손동작 실행 내용 종료 조건
손바닥을 펼쳐 이동 손바닥 중심을 기준으로 커서 이동 다른 동작 시작 또는 해당 손 추적 유실
나머지 손가락을 펼치고 검지 접기 왼쪽 버튼 누름 검지 펴기 또는 강제 종료
검지를 접은 채 이동 왼쪽 버튼을 누른 상태로 커서 이동 검지 펴기 또는 강제 종료
검지 다시 펴기 왼쪽 버튼 해제 해당 누름·드래그 종료
같은 위치에서 검지를 접었다 펴기 누름·해제를 통한 왼쪽 클릭 한 번의 누름·해제로 완료
손바닥 상태에서 중지만 접었다 펴기 펼침 확인 시 오른쪽 클릭 한 번 완료 후 재시작 조건 대기

검지 끝 대신 손바닥 중심을 커서 기준점으로 사용한다. 검지를 접은 동안에도 손바닥 위치를 추적한다. 왼쪽 버튼 누름·해제로 이미 클릭을 구성하므로 추가 click 명령을 보내지 않는다.

우클릭 준비 중에는 커서를 고정하고, 완료 시 고정 위치에서 오른쪽 클릭을 한 번 실행한다. 준비 도중 추적 유실, 중단 또는 다른 자세로 변경되면 우클릭을 취소한다. CAPTURE에서는 우클릭을 사용하지 않는다.

마우스 조작을 시작한 손의 제어권을 해당 조작 동안 유지한다. 다른 손이 나타나도 자동으로 바꾸지 않는다. 집기는 자체 객체 이동·양손 조작에 사용하며 실제 왼쪽 클릭이나 드래그를 발생시키지 않는다. 검지 접기와 엄지·검지 집기를 동시에 판정하지 않도록 엄지 및 나머지 손가락 조건을 구분한다. 구체적인 굽힘 임계값은 후속 판정 규칙에서 정한다.

5.4 스크롤과 탭 전환

스크롤은 BROWSER의 활성 상태에서 검지·중지를 펼친 채 손을 위아래로 움직여 수행한다. 위로 이동하면 페이지 위쪽, 아래로 이동하면 페이지 아래쪽으로 스크롤한다. 손을 멈추면 스크롤도 멈추며, 이동량에 비례해 스크롤 양을 결정한다. 작은 떨림은 무시한다.

같은 자세의 가로 이동은 기존 브라우저 탭 전환에 사용하므로, 동작 시작 후 유효한 이동이 나타나면 가로·세로 중 하나의 역할을 결정한다.

판정 처리
세로 이동이 명확함 스크롤 시작, 커서 위치 고정
가로 이동이 명확함 좌우 방향에 맞는 탭 전환 한 번
대각선 등 방향이 모호함 명령 없이 방향 판정 대기
손 모양 해제 현재 동작 종료, 다음 동작에서 방향 재판정

한 동작 안에서 스크롤과 탭 전환을 오가지 않는다. 손바닥을 펼치면 커서 이동으로 복귀할 수 있다. 브이로 활성화한 직후에는 활성화에 사용한 자세를 해제한 다음 새 두 손가락 동작을 시작해야 한다. 브라우저 대상 스크롤·탭 전환은 실행 직전 Chrome 활성 여부를 확인한다.

5.5 일반 모드 전환

IMAGE와 BROWSER의 전환은 프로그램의 모드 선택 버튼으로 수행한다. 손동작 마우스와 물리 마우스 모두 같은 UI 요청을 발생시킨다. 별도의 일반 모드 전환 제스처는 두지 않는다.

전환 전 모드 버튼 선택 후
IMAGE + ACTIVE BROWSER + ACTIVE
BROWSER + ACTIVE IMAGE + ACTIVE
IMAGE 또는 BROWSER + WAITING 선택한 모드 + WAITING
현재 모드 버튼 재선택 상태 유지

전환 시 기존 조작을 종료하고 눌린 입력을 해제하며, 과거 일반 명령과 제스처 이력을 초기화한다. 활성 상태를 유지하더라도 이전 동작을 새 모드에서 이어 실행하지 않고 새로운 시작 조건을 확인한다. IMAGE의 현재 이미지 배치 등 작업 결과는 모드 전환만으로 초기화하지 않는다.

BROWSER에서는 5.12의 비활성화 제어 패널을 사용하여 버튼 클릭이 기존 Chrome 포커스를 빼앗지 않도록 한다. IMAGE에서 BROWSER로 처음 진입했을 때 Chrome이 활성 창이 아니라면 사용자가 공통 커서로 Chrome을 선택한다. Chrome 활성화를 임의로 강제하지 않는다. 창 조회 실패 또는 Chrome 비활성 상태에서는 브라우저 전용 명령을 차단하고 안내하되 공통 마우스는 허용한다.

CAPTURE에서 다른 모드 버튼을 직접 선택하는 경로는 제공하지 않는다. 저장 또는 취소로 캡처를 끝내고 이전 모드로 복귀한 뒤 전환한다.

5.6 캡처 진입

캡처 진입 경로는 프로그램의 캡처 버튼 클릭과 양손 카메라 프레임 제스처 두 가지다. 두 경로는 공통 제어의 동일한 캡처 진입 절차를 사용한다.

카메라 프레임 제스처는 양손의 엄지·검지를 벌려 각각 ㄴ자 형태로 만들고, 두 손을 반대 방향으로 배치해 프레임 모양을 일정 시간 유지하는 동작이다. 손끼리 맞닿을 필요는 없다. 엄지·검지가 가까워지는 집기와 구분한다. 유지 시간, 방향 및 간격 허용치는 후속 인식 실험으로 정한다.

진입 경로 조건 진입 후 활성 상태
손동작으로 캡처 버튼 클릭 ACTIVE ACTIVE 유지
물리 마우스로 캡처 버튼 클릭 ACTIVE 또는 WAITING 기존 상태 유지
양손 카메라 프레임 ACTIVE, IMAGE 또는 BROWSER ACTIVE 유지

진입이 확정되면 진행 중 조작을 종료하고 입력을 해제한 뒤 이전 모드를 저장한다. mode를 CAPTURE로 변경하고 선택 화면을 표시한다. 제스처로 진입한 경우 카메라 프레임 자세를 해제한 다음 양손 집기를 새로 시작해야 영역을 조절할 수 있다. CAPTURE 안에서는 캡처 진입 요청을 중복 실행하지 않는다.

대기 상태에서 물리 마우스로 캡처에 진입하면 WAITING을 유지한다. 손동작 영역 조절과 버튼 조작은 브이로 활성화한 뒤 가능하다. 물리 마우스로 취소는 가능하다. 물리 마우스에 의한 영역 그리기는 현재 필수 범위에 포함하지 않는다.

5.7 캡처 내부 상태와 영역 조절

캡처 진행 상태는 전체 activation과 별도로 관리한다.

내부 상태 의미
SELECTING 영역을 만들거나 수정하는 상태
READY 유효한 선택 영역을 유지하며 저장·취소를 기다리는 상태
SAVING 선택 UI 숨김과 촬영·저장이 진행 중인 상태
ERROR 저장 오류 후 재시도·취소를 기다리는 상태

캡처 진입 직후 SELECTING으로 시작한다. 양손 집기를 새로 시작하면 각 집기 위치를 대각선 꼭짓점으로 사용해 사각형을 갱신한다. 손이 교차해도 좌표의 최솟값과 최댓값으로 사각형을 계산한다.

집기를 풀면 마지막 영역을 유지하고, 영역이 유효하면 READY가 된다. 양손 조작 중 한 손의 유실이 확정되어도 전체 활성 상태는 유지하고 해당 영역 조절만 종료한다. 마지막 영역이 유효하면 READY, 아니면 SELECTING으로 남는다. 이후 새 양손 집기로 다시 조절할 수 있다.

영역 조절 중에는 같은 손의 움직임을 커서 이동이나 클릭으로 중복 해석하지 않는다. 집기를 해제하고 손바닥 커서 동작을 새로 시작하면 저장·취소 버튼을 선택할 수 있다. 저장 버튼은 유효 영역이 있고 영역 조절이 끝난 READY에서만 활성화한다. 최소 영역 크기는 후속 규칙에서 정한다.

5.8 캡처 저장과 일반 취소

READY에서 저장 버튼을 누르면 최종 영역을 고정하고 SAVING으로 전환한다. 중복 저장 요청과 영역 변경을 차단한 뒤 다음 순서로 처리한다.

  1. 캡처 영역, 요청 ID 및 현재 활성 상태를 기록한다.
  2. 선택 영역 표시, 저장·취소 버튼 등 캡처용 화면 요소를 숨긴다.
  3. 숨김과 화면 반영을 확인한다.
  4. 확정된 실제 픽셀 영역을 촬영하고 PNG 파일로 저장한다.
  5. 성공 결과를 받은 뒤 이전 모드로 복귀하고 저장 경로를 안내한다.

저장 완료 시 최신 활성 상태를 유지한다. 저장 도중 중단 요청이 없었다면 ACTIVE는 ACTIVE로, WAITING은 WAITING으로 유지한다. 물리 마우스로 저장해도 이 원칙은 동일하다.

SELECTING, READY 또는 ERROR에서 취소 버튼을 누르면 새로운 저장을 수행하지 않고 선택 화면을 닫은 뒤 이전 모드로 복귀한다. 취소 자체는 activation을 변경하지 않는다. SAVING 중에는 일반 취소 버튼을 제공하지 않으며, 이미 실행한 파일 저장을 단순 취소할 수 있다고 표시하지 않는다.

저장 실패 시 ERROR로 전환하고 기존 영역을 보존한다. 선택 화면에 오류와 재시도·취소를 표시한다. 재시도는 화면을 다시 촬영하는 새 저장 시도로 처리하며 중복 파일명 충돌을 피한다. 실패 결과에 부분 파일이 남았다면 캡처 저장 모듈이 이를 정리하거나 사용자에게 상태를 보고한다.

5.9 캡처 중 숫자 3과 오류 처리

캡처 단계 숫자 3 중단 처리
SELECTING 또는 READY 조작 종료, 입력 해제, 저장 없이 캡처 취소, 이전 모드 + WAITING 복귀
ERROR 재시도 없이 캡처 종료, 이전 모드 + WAITING 복귀
SAVING, 촬영·저장 실행 전 대기 중 저장 요청 취소, 이전 모드 + WAITING 복귀
SAVING, 촬영·저장 실행 시작 후 즉시 WAITING 및 입력 해제, 실행 중 작업 결과를 받은 뒤 이전 모드로 복귀

이미 시작한 저장은 성공할 수 있으므로 결과를 숨기거나 취소되었다고 단정하지 않는다. 성공하면 경로를, 실패하면 오류를 알린다. 중단 이후 도착한 결과가 프로그램을 ACTIVE로 바꾸지 않도록 한다. 실행 중 저장의 식별자는 결과 확인용으로 유지하되 다른 과거 일반 명령을 되살리지 않는다.

단순 손 유실은 해당 조작 종료로 처리하고 activation을 유지한다. 카메라 연결 실패 등 프로그램 수준의 입력 오류는 진행 중 조작을 정리하고 오류를 표시한다. 복구 후 자동 조작 재개 여부 등 장치 오류 상세 정책은 후속 오류 처리 항목에서 정의한다.

5.10 상태 표시와 충돌 처리

UI는 현재 모드, ACTIVE 또는 WAITING, 활성화 자세 해제 대기 여부, 진행 중 조작, 캡처 내부 상태와 주요 오류를 표시한다. 저장 성공 여부는 실제 실행 결과에 따라 표시한다.

판정 우선순위는 전체 중단 및 입력 해제, 진행 중 조작의 종료·취소, 승인된 연속 조작 갱신, 새로운 일반 동작 시작 순서로 적용한다. 카메라 프레임 진입이 확정되면 기존 커서 등 일반 조작을 정리하고 캡처로 전환한다. 숫자 3과 함께 판정되면 중단을 우선한다.

모드 전환과 캡처 진입·복귀는 context_version을 갱신한다. 캡처에서 영역 조절만 끝나거나 손 개수가 바뀐 경우에는 전체 맥락을 초기화하지 않는다. 전환 후 기존 손 자세만으로 클릭·드래그·스크롤이 자동 재시작되지 않도록 새 시작 조건을 확인한다.

손가락 굽힘 임계값, 유지 시간, 방향 판정 거리, 스크롤 감도와 여러 손의 동시 시작 선택 기준은 후속 세부 판정·충돌 규칙에서 정한다. 이 값들은 본 항목의 상태 전환 의미를 변경하지 않는다.

5.12 창 구성과 포커스 정책

IMAGE에서는 이미지 캔버스와 파일 열기·폴더 열기·모드·캡처 버튼을 포함하는 일반 메인 창을 사용한다. BROWSER로 전환하면 이미지 메인 창을 숨기고 화면 모서리 안쪽의 작은 항상 위 제어 패널을 표시한다. 패널에는 모드, ACTIVE/WAITING, 현재 동작, 중단·캡처·IMAGE 전환 버튼과 더보기 메뉴를 표시한다. 더보기에는 이미지 파일 열기·폴더 열기·설정·저장 폴더 선택을 제공하고 각 항목을 A.4의 요청으로 연결한다. 상태 갱신과 안내 표시만으로 창을 활성화하지 않는다.

BROWSER 패널은 마우스 버튼을 받을 수 있으면서 클릭으로 활성 창이 되지 않는 창으로 구현한다. 항상 위 표시와 비활성화 동작은 별개 요구사항이다. 키보드 입력 위젯은 이 패널에 넣지 않는다. Windows에서 패널의 모드·중단·캡처·미리보기 버튼을 실제 클릭한 전후의 활성 창 핸들을 비교해 검증한다. IMAGE 버튼을 선택하면 일반 메인 창을 표시·활성화하는 것은 의도된 전환이다.

카메라 미리보기는 IMAGE의 접이식 보조 영역, BROWSER의 접이식 패널 영역에 표시한다. 기본값은 접힘이다. 미리보기는 좌우 반전한 영상과 인식 상태를 표시하며 자체 조작 대상이 아니다. 펼침·접힘은 Chrome 포커스를 바꾸지 않는다. 일반 안내는 패널 안에 표시하고 입력 포커스를 요구하는 팝업을 자동으로 띄우지 않는다.

파일 선택·저장 폴더 선택·설정·오류 확인처럼 포커스가 필요한 대화상자는 일반 창으로 띄운다. 열기 전에 진행 중 조작을 종료하고 입력 해제를 확인한 뒤 ui_interaction_lock=true로 설정한다. 잠금 중에는 브라우저 단축키·콘텐츠 제스처·캡처 진입을 차단하지만 대화상자 선택을 위한 공통 커서·왼쪽 클릭과 전체 중단은 허용한다. 대화상자에서 실제 드래그·우클릭·스크롤 제스처는 초기 버전에서 사용하지 않는다. 물리 키보드·마우스는 그대로 사용할 수 있다.

대화상자가 닫히면 잠금을 해제하고 새 동작 준비 절차를 거친다. 종료 시점의 activation을 유지하므로 대화상자 도중 숫자 3으로 중단했다면 자동 재활성화하지 않는다. BROWSER로 돌아가도 Chrome 포커스를 강제 복원하지 않고 사용자가 선택하게 한다. 캡처 선택 오버레이는 정상적으로 활성화·입력 수신할 수 있으며 저장·취소 후에는 비활성 제어 패널 표시만 복구한다. 대화상자 종료와 동일하게 Chrome 포커스를 강제 복원하지 않는다. BROWSER 복귀 시 비활성이라면 CHROME_NOT_ACTIVE 안내를 표시하고 사용자가 Chrome을 선택하도록 한다.

5.13 대화상자와 미리보기 데이터 경로

UIRequestType에 REQUEST_OPEN_IMAGES, REQUEST_OPEN_IMAGE_FOLDER, REQUEST_CHOOSE_SAVE_DIR, REQUEST_OPEN_SETTINGS를 추가한다. payload는 빈 데이터이며 CAPTURE·SAVING·기존 대화상자 진행 중에는 거절한다. Controller가 입력 해제를 확인한 뒤 UI_OPEN_DIALOG 명령을 보내며 payload는 dialog_id: str, kind: IMAGE_FILES/IMAGE_FOLDER/SAVE_DIR/SETTINGS다. 선택 창이 열리기 전에 UI가 임의로 파일 대화상자를 먼저 띄우지 않는다.

UiBridge는 종료 시 REQUEST_DIALOG_FINISHED를 발행한다. payload는 dialog_id: str, outcome: ACCEPTED/CANCELLED/FAILED, selection: 종류별 자료형 또는 None이다. IMAGE_FILES는 paths: tuple[str,...], IMAGE_FOLDER·SAVE_DIR은 path: str, SETTINGS는 변경한 허용 설정 키·값을 담는다. Controller가 저장 폴더 선택 결과를 기존 REQUEST_SET_SAVE_DIR 처리 함수로 연결하고, 이미지 결과는 UI_LOAD_IMAGES로 연결한다. 취소·실패도 반드시 잠금을 해제한다. 대화상자 생성 실패는 UI_OPEN_DIALOG의 실패 결과로 처리한다.

REQUEST_SET_PREVIEW_VISIBLE의 payload는 visible: bool이며 캡처 외 상태에서 허용한다. 공통 제어는 UI_SET_PREVIEW_VISIBLE(visible)로 전달한다. 대화상자·미리보기 상태 필드는 부록 A.5를 따른다. 이 필드 추가는 부록 A의 메시지 버전 3 계약으로 처리한다.

PreviewFrame은 schema_version, frame_id, captured_at_ms, width, height, rgb_bytes: bytes를 가진다. 픽셀은 원본 방향의 RGB, 행 우선, 행 패딩 없음으로 전달하며 UI가 미리보기에만 반전한다. VisionWorker.preview_ready → UiBridge.on_preview(frame: PreviewFrame)로 연결하고 메인 UI 스레드에서 이미지 객체를 만든다. 표시할 때 최대 10FPS, 최신 한 장만 유지하며 손 추적 메시지와 별도 경로로 전달한다. Controller.preview_enabled_changed(bool) → VisionWorker.set_preview_enabled(enabled: bool)로 생산 여부를 제어한다. 미리보기가 꺼지면 영상 사본 생산을 중단한다.

5.14 앱 수명주기와 일반 입력 허용

AppPhase는 STARTING, CONFIG_ERROR, RUNNING, SHUTTING_DOWN으로 정의한다. CameraStatus는 DISCONNECTED, CONNECTING, CONNECTED, RECONNECTING, FAILED다. 실행 모드 ExecutionMode는 WINDOWS_REAL, DEV_SIMULATED, REPLAY로 구분한다. 전체 목록과 필드는 부록 A를 따른다.

Controller는 input_blocked_reasons를 frozenset[InputBlockReason]으로 관리한다. 동시 오류를 덮어쓰지 않고 원인별로 추가·제거한다. 설정 준비·장치 준비·입력 해제·화면 재초기화·작업 정지의 완료 보고를 받은 경우에만 해당 사유를 제거한다.

일반 동작을 허용하려면 app_phase=RUNNING, camera_status=CONNECTED, activation=ACTIVE, ready_for_gestures=true, release_pending=false, input_blocked_reasons가 비어 있어야 한다. 대화상자 잠금은 이 조건에 추가되는 대상별 제한이며 공통 마우스는 5.12의 예외를 적용한다. 정상 손 미검출은 CAMERA_UNAVAILABLE을 추가하지 않는다.

브이 활성화 수락에도 RUNNING·CONNECTED·차단 사유 없음·입력 상태 확인·해제 완료와 200ms 이내 CLEAR 조건을 요구한다. CLEAR가 오래되면 활성화를 거절하지만 손 조작이 없던 상태를 임의로 정상으로 갱신하지 않는다. CLEAR가 회복되어도 자동 활성화하지 않는다.

REQUEST_USE_DEFAULT_CONFIG는 CONFIG_ERROR에서만 허용한다. REQUEST_RECONNECT_CAMERA는 STARTING/SHUTTING_DOWN 또는 CONNECTING/RECONNECTING에서 거절하고, 설정이 유효한 RUNNING에서만 수행한다. CONFIG_ERROR에서는 기본값 사용 또는 종료를 먼저 선택한다. RUNNING은 장치 오류 화면도 포함할 수 있으며 camera_status=FAILED와 차단 사유로 입력을 막는다. UI 버튼의 활성 여부도 이 필드로 결정한다.

6.1 적용 원칙

이하 내용은 구현 기준으로 채택하는 설계안이다. 수치가 포함된 인식 조건과 성능 목표는 측정 결과가 아닌 초기 설정 및 검증 목표다. 12번 절차로 측정한 뒤 확정값을 기록한다. 사용자와 확정한 손 모양과 기능 의미는 유지하며, 임계값 조정으로 의미를 바꾸지 않는다.

이 절에서 기능 설명의 좌우는 사용자가 보는 반전 미리보기 기준이다. GestureEvent의 direction은 원본 카메라 기준이며 공통 제어가 9.4에 따라 한 번 변환한다. 왼쪽은 이전 이미지·이전 페이지·이전 탭, 오른쪽은 다음 이미지·다음 페이지·다음 탭으로 통일한다. 이미지가 첫 장이나 마지막 장이면 더 넘기지 않고 경계 안내만 표시한다.

6.3 객체 이동과 확대

집기 위치는 엄지 끝과 검지 끝의 중점으로 정의한다. IMAGE에서 집기 시작 위치에 있는 최상위 객체를 선택한다. 객체가 없으면 이동을 시작하지 않는다. 시작 시 집기 위치와 객체 원점의 차이를 보존하여 객체가 손 위치로 갑자기 뛰지 않도록 한다.

양손 확대 대상은 현재 선택 객체로 고정한다. 선택 객체가 없으면 화면의 주 이미지, 그것도 없으면 실행하지 않는다. 양손 시작 거리 d0와 객체 배율 s0를 저장하고 s=s0×d/d0로 계산한다. 초기 허용 배율은 원본 크기 대비 0.25~4.0이다. 양손 중심의 시작 위치를 확대 기준점으로 사용하고 확대 중 별도 이동을 동시에 적용하지 않는다.

BROWSER 확대는 연속 비율을 그대로 픽셀 크기로 적용하지 않고 단계별 확대·축소 명령으로 변환한다. 시작 비율 대비 1.15배 증가마다 한 단계 확대, 1/1.15배 감소마다 한 단계 축소한다. 한 단계 실행 후 기준 거리를 갱신하고 최대 초당 4단계로 제한한다. 제스처 종료 시 잔여량을 버린다. 브라우저 자체 배율은 별도 읽기 기능 없이 추정해 표시하지 않는다.

6.5 이미지 콘텐츠와 슬라이드 정의

초기 지원 형식은 확장자 대소문자를 구분하지 않는 PNG, JPG, JPEG다. 여러 파일 선택과 단일 폴더 불러오기를 제공한다. 폴더는 바로 아래 파일만 읽고 하위 폴더는 재귀 탐색하지 않는다. 같은 절대 경로는 한 번만 포함하고 파일명 숫자 구간을 숫자로 비교하는 자연 정렬을 적용한다. 이름이 같으면 전체 경로로 순서를 고정한다.

슬라이드는 불러온 이미지 목록을 한 장씩 표시하는 기능이다. PPT·PPTX·PDF 해석, 애니메이션·영상 재생은 초기 범위에 넣지 않는다. 기존 문서의 카드는 별도 객체 종류가 아니라 이미지 객체를 뜻하며 이후 용어는 이미지 객체로 통일한다. 초기 캔버스에는 현재 슬라이드 이미지 객체 하나를 표시한다.

파일은 확장자와 실제 디코딩 성공 여부를 함께 검사한다. JPEG의 방향 메타데이터를 표시 방향에 반영하고 PNG 투명 부분은 캔버스 배경 위에 표시한다. 읽기 실패 파일은 제외하고 파일명과 사유를 안내한다. 유효 파일이 하나 이상이면 성공 목록으로 교체하고 첫 이미지를 중앙 맞춤 크기로 표시한다. 모두 실패하거나 선택을 취소하면 기존 목록·현재 위치를 유지한다. 시작 시 콘텐츠가 없으면 열기 안내를 표시하고 슬라이드·객체 조작 명령을 무시한다.

목록 교체 전에 진행 중 객체 조작을 종료한다. 슬라이드별 위치·배율은 현재 세션에서 보존하고, 초기화 동작은 현재 슬라이드만 중앙 맞춤 상태로 되돌린다. 새로 불러오기와 프로그램 재시작에서는 이전 배치를 자동 복원하지 않는다.

UI_LOAD_IMAGES의 payload는 paths: tuple[str,...] 또는 directory: str 중 정확히 하나다. 파일 수집·디코딩은 ui/image_loader.py의 QThreadPool 작업으로 수행한다. 작업에서는 QImage를 생성하고 QPixmap·위젯을 생성하거나 수정하지 않는다. 결과 전달 뒤 QImage를 수정하지 않으며 메인 스레드에서만 QPixmap으로 변환하고 위젯에 반영한다. 완료 경로와 요청 검증은 13.8을 따른다. 결과 output은 loaded_count: int, rejected_files: tuple[FileLoadFailure,...], current_object_id: str 또는 None이다. FileLoadFailure는 path와 reason을 갖는다. 성공 파일이 0개면 CONTENT_LOAD_FAILED, 일부만 실패하면 SUCCESS와 제외 목록을 반환한다. 진행 중에는 ui_interaction_lock을 유지하고 중복 불러오기를 차단한다.

6.6 캔버스와 실제 마우스의 역할

이미지 캔버스는 운영체제 마우스 누름·이동·휠 이벤트로 이미지 위치·크기를 변경하지 않는다. 객체 조작은 승인된 UI_MOVE·UI_SCALE·UI_RESET 명령으로만 수행한다. 실제 마우스 드래그와 집기 이벤트가 동일 객체를 두 번 이동시키는 경로를 만들지 않는다.

캔버스 클릭은 창 포커스 획득에는 사용할 수 있지만 객체 드래그를 시작하지 않는다. 휠 확대, 마우스 드롭에 의한 파일 열기, 객체 우클릭 메뉴는 초기 버전에서 사용하지 않는다. 파일 열기·모드·저장 등 UI 버튼은 실제 마우스와 손동작으로 생성한 마우스 입력을 정상 처리한다. 두 입력의 출처를 추정해 분기하지 않고 위젯 역할에 따라 구분한다.

실제 드래그는 브라우저 등 외부 창에서 계속 사용할 수 있다. 자체 이미지 편집에 물리 마우스 이동을 추후 추가하려면 별도 기능으로 설계하고 집기와 공유할 객체 조작 경로를 정의한 뒤 반영한다.

7.1 특징 계산 기준

관절 인덱스는 선택한 손 모델의 공통 인덱스 표를 코드와 문서에 함께 고정한다. 초기 구현은 손목 0, 엄지 끝 4, 검지 끝 8, 중지 끝 12, 약지 끝 16, 소지 끝 20을 사용한다. 손바닥 중심은 손목과 네 손가락 뿌리 관절 0·5·9·13·17의 평균으로 계산한다.

손가락 각도와 손 크기 비율을 계산할 때는 x에 영상 너비, y에 영상 높이를 곱한 영상 평면 좌표를 사용한다. 손 크기 L은 5번과 17번 관절 사이 거리로 정의한다. L이 20픽셀보다 작거나 좌표가 비정상이면 해당 프레임으로 새 동작을 시작하지 않는다. 깊이 z는 초기 판정의 필수 조건으로 사용하지 않는다.

검지·중지·약지·소지는 PIP와 DIP 관절 각도를 사용한다. 두 각도가 모두 160도 이상이면 펼침, PIP가 120도 이하이면 접힘으로 판정한다. 중간 구간은 UNKNOWN으로 두고 이미 진행 중인 동작에서는 직전 상태를 최대 100ms만 유지한다. 엄지는 MCP와 IP 각도가 각각 150도 이상이며 엄지 끝과 검지 뿌리 거리가 0.6L 이상일 때 펼침, IP가 130도 이하 또는 해당 거리가 0.4L 이하일 때 접힘으로 시작한다. 이 기준은 2차원 투영에 의한 초기 휴리스틱으로, 정면 및 가벼운 회전 자세를 대상으로 보정한다.

7.3 클릭과 드래그 판정

손바닥 자세를 120ms 확인한 손에 마우스 시작 자격을 부여한다. 같은 손의 검지가 접힘으로 100ms 유지되고 엄지·중지·약지·소지가 펼침이면 INDEX_BEND START를 발행한다. 시작 시 버튼을 누른다. 검지를 펴기 시작한 첫 프레임부터 이동을 잠시 고정하고, 펼침이 80ms 확인되면 END와 버튼 해제를 수행한다. 다른 자세로 변경되거나 손 ID가 바뀌면 CANCEL로 해제한다.

버튼을 누른 직후 손바닥 이동이 시작점에서 6 논리 픽셀 상당의 거리(9.4에 따라 실제 픽셀로 변환)를 넘기 전까지 커서를 시작 위치에 고정한다. 이를 넘으면 드래그로 보고 현재 손 이동을 반영한다. 같은 위치의 누름·해제는 운영체제 클릭이 된다. 초기 손동작 인터페이스는 더블클릭 전용 제스처를 제공하지 않는다.

우클릭은 동일한 손바닥 준비 상태에서 중지가 100ms 접히고 다른 손가락이 펼쳐진 경우 시작한다. 중지를 80ms 다시 펼쳤을 때 고정 위치에서 한 번 실행한다. 2초 안에 정상 펼침을 완료하지 못하면 취소한다. 중지 접힘과 검지 접힘이 함께 관측되면 둘 다 새로 시작하지 않는다.

7.4 쓸기와 스크롤

쓸기는 원본 카메라 좌표에서 손바닥 중심의 이동으로 판정한다. 150~600ms 안에 원본 기준 가로 이동이 영상 너비의 0.15 이상이고 |dx|가 |dy|의 1.8배 이상이면 한 번 실행한다. 손 모양은 한 손가락 또는 두 손가락 조건을 이동 구간 내 유지해야 한다.

두 손가락 동작은 이동량 0.04 이상에서 주축 비율 1.8을 만족하면 가로 또는 세로로 역할을 잠근다. 가로 잠금 후 쓸기 기준을 충족하면 탭 전환을 한 번 실행한다. 세로 잠금에서는 판정 이전 이동을 소급 실행하지 않고 이후 세로 이동부터 스크롤로 누적한다. 초기 감도는 영상 높이의 0.04 이동당 한 스크롤 단계, 최대 초당 10단계다. 이동이 멈추면 새 명령을 보내지 않는다.

검지만 펼친 BROWSER 동작은 가로 쓸기와 원 그리기를 함께 관측하되 경로 직선성이 0.9 이상일 때만 쓸기로 확정한다. 직선성은 시작·끝 직선거리/전체 경로 길이다. 곡선이면 원 판정을 기다리고, 한 경로에서 두 명령을 실행하지 않는다.

원은 시계·반시계 모두 허용한다. 엄지 올리기는 손의 좌우와 무관하게 엄지 펼침/나머지 접힘으로 판정하고 화면상 위 방향까지 강제하지 않는다. 카메라 프레임은 반대 방향의 두 ㄴ자 형태를 기준으로 하며 손을 겹칠 필요가 없다. 두 손의 개별 각도·거리 조건과 시간 조건을 함께 만족해야 한다.

형태 조건에서 가리키기는 검지만 펼치고 나머지는 접음, 열린 손바닥은 다섯 손가락 펼침으로 정의한다. 집기는 엄지·검지 끝 거리 조건을 우선 사용하되 검지 접기 마우스 세션이 이미 진행 중이면 새 집기로 전환하지 않는다.

포인터에서 슬라이드 쓸기가 확정되면 포인터를 숨기고 한 번 전환한다. 주먹 후 펼치기 완료 프레임의 열린 손바닥은 커서 시작에 재사용하지 않고 180ms 준비 구간을 거친다.

7.6 추적과 보정

손 ID 대응은 이전 손바닥 중심과 관절 형태를 사용하고, 왼손·오른손 분류는 보조 정보로 사용한다. 후보가 모호한 손 교차 상황에서는 기존 손을 임의로 바꾸지 않고 관련 조작을 취소한다. 손이 보이지 않는 첫 프레임부터 그 손의 이동 갱신을 멈추며, 유실 확정 시간까지 회복되면 동일성이 확실한 경우에만 기존 조작을 이어간다. ID가 바뀌면 새 시작이 필요하다.

커서·UI·캡처 좌표는 손별 지수 보정을 적용한다. alpha=1-exp(-dt/60ms), filtered=alpha×new+(1-alpha)×previous로 계산한다. dt는 유효 관측 간격이다. 제스처가 바뀌거나 손 ID가 바뀌면 보정 이력을 초기화한다. 숫자 3 중단 판정을 좌표 보정 때문에 지연시키지 않는다.

7.7 Hand Landmarker 실행과 좌우 라벨

MediaPipe Tasks Hand Landmarker를 사용하고 기존 solutions.hands API와 혼용하지 않는다. 인식 작업 스레드에서 VIDEO 모드의 detect_for_video를 순차 호출한다. 실시간 웹캠이어도 타임스탬프가 있는 순차 프레임을 처리하므로 VIDEO 모드를 사용할 수 있다. LIVE_STREAM의 비동기 콜백 경로는 초기 버전에 추가하지 않는다.

num_hands=2, min_hand_detection_confidence=0.5, min_hand_presence_confidence=0.5, min_tracking_confidence=0.5를 명시한다. 각각 검출·존재·추적 판단의 설정이며 handedness_score와는 다르다. 값의 허용 범위는 0~1이다. OpenCV 프레임은 BGR에서 RGB로 변환한 뒤 MediaPipe 입력으로 만들고 좌우 반전은 하지 않는다.

촬영 시각을 밀리초 정수로 전달하며 같은 Landmarker 인스턴스의 타임스탬프는 엄격히 증가해야 한다. 동일 밀리초 또는 역순 프레임은 폐기하고 시간값을 임의로 뒤로 조작하지 않는다. 대기 프레임이 쌓이면 최신 프레임을 우선하고 하나의 인스턴스를 여러 스레드에서 동시에 호출하지 않는다. 장치 재연결로 인스턴스를 재생성할 때에도 프로그램 공통 시계는 유지한다. Hand Landmarker 공식 안내

기존 Hands 안내에는 거울 입력 가정이 있지만, 이를 근거로 Tasks의 모든 모델에 무조건 라벨 교환을 적용하지 않는다. 고정한 MediaPipe 버전·모델 해시·카메라 입력 반전 여부의 조합에서 실제 왼손·오른손을 각각 단독 촬영하고 최소 20개 유효 프레임을 확인한다. 원본 라벨과 실제 손이 일치하면 handedness_swap=false, 반대이면 true로 고정한다. 일관되지 않으면 UNKNOWN으로 처리하고 원인을 확인한다. 기존 Hands의 handedness 안내

초기 handedness_swap=null은 미검증을 의미한다. 이때 raw_handedness는 보관하되 공개 handedness는 UNKNOWN으로 내보낸다. 일반 동작은 안정적인 hand_id로 처리하므로 라벨 미확정만으로 손 추적을 중단하지 않는다. 배포 전에는 검증 결과와 모델 해시를 기록한다. 미리보기 반전은 이 설정을 자동으로 변경하지 않으며 라벨 보정은 tracker.py 한 곳에서만 수행한다.

7.8 스크롤과 숫자 3의 엄지 구분

두 손가락 스크롤과 숫자 3은 검지·중지 펼침, 약지·소지 접힘을 공유한다. 엄지는 7.1의 펼침·접힘·UNKNOWN 세 상태로 판정하며 숫자 3 중단에는 현재 프레임의 명확한 펼침만 인정한다. UNKNOWN에서 직전 펼침 상태를 유지한 값을 중단 유지 시간에 합산하지 않는다.

스크롤 중 엄지가 UNKNOWN 또는 펼침 후보가 되면 즉시 새 스크롤 출력을 보류하고 커서와 activation은 유지한다. 네 손가락 조건이 맞고 엄지가 명확히 펼쳐진 상태가 연속 350ms 유지될 때만 숫자 3을 확정한다. 불확실 또는 접힘이 나타나면 중단 타이머를 초기화한다. 의도적인 숫자 3은 스크롤 중에도 항상 판정한다.

엄지 접힘이 120ms 다시 확인되고 나머지 두 손가락 자세가 유효하면 기존 세로 역할로 스크롤을 재개할 수 있다. 이때 기준 위치를 현재 위치로 재설정하고 보류 중 이동량은 버려 갑자기 스크롤되지 않도록 한다. 후보 상태가 1초 이상 지속되거나 다른 손가락 자세로 바뀌면 스크롤 세션만 종료한다. 프로그램은 ACTIVE를 유지한다.

350ms 동안 잘못 펼침으로 분류되는 오인식 자체를 시간 규칙만으로 완전히 없앨 수는 없다. 정면·가벼운 회전·엄지가 느슨하게 벌어진 자세에서 두 손가락 스크롤과 의도적 중단을 각각 측정하고 펼침·접힘 기준을 보정한다. 정적 숫자 3과 실제 스크롤 중 숫자 3 전환을 별도 시험한다.

8 명령 충돌과 중복 실행 방지

8.1 우선순위와 조작 소유권

초기 버전에서는 일반 조작 세션을 한 번에 하나만 승인한다. 단, 활성화·중단 감지와 양손 전환 후보 검사는 계속 수행한다. IMAGE의 발표 포인터와 동일한 검지 자세의 쓸기는 하나의 세션 안에서 판정하며, 쓸기 확정 시 포인터를 종료하고 슬라이드 명령으로 전환한다. 참여하지 않은 손의 등장·소멸은 진행 중 조작을 바꾸지 않는다.

우선순위는 다음과 같다.

  1. 종료·전체 중단·입력 해제 및 장치 오류
  2. 진행 중 조작의 정상 종료·유실 취소
  3. 명시적 UI 모드 변경·캡처 버튼 요청
  4. 양손 카메라 프레임과 양손 조작 전환
  5. 진행 중 조작 갱신
  6. 새로운 단발 명령과 한 손 조작

실제 버튼이 눌린 동안에는 새로운 일반 제스처나 캡처 제스처를 시작하지 않는다. 먼저 버튼 해제 또는 중단이 필요하다. 모드 버튼의 정상 클릭으로 들어온 전환 요청은 버튼 해제 뒤 처리한다.

동시에 두 손이 같은 한 손 조작을 시작하면 자세 조건을 먼저 충족한 손을 선택한다. 같은 프레임이면 이전 제어 손, 이전 손이 없으면 hand_id 문자열 순서로 결정한다. 선택 규칙은 손잡이를 강제하는 사용자 설정이 아니라 충돌 시에만 적용하는 결정 규칙이다.

8.2 한 손에서 양손으로 전환

IMAGE에서 한 손 집기 시작 후 200ms 동안 두 번째 집기를 기다린다. 이 시간에는 선택 강조만 표시하고 객체를 이동하지 않는다. 두 번째 손이 참여하면 양손 확대를 시작하고, 없으면 한 손 이동을 시작한다.

이미 한 손 이동 중 두 번째 손의 집기가 120ms 확정되면 현재 위치에 객체를 놓고, 현재 배율·양손 거리를 새 기준으로 양손 확대를 시작한다. 기존 interaction_id는 END로 닫고 새로운 ID를 부여한다. 별도 마우스 입력은 발생시키지 않는다.

양손 동작이 종료되면 마지막 결과를 유지한다. 남아 있는 손도 집기를 한 번 해제한 뒤 새로 집어야 한 손 이동을 시작한다. BROWSER와 CAPTURE에서는 첫 집기에 단독 명령이 없고 양손이 준비되면 시작한다. 양손 시작 거리가 평균 손 크기의 1.5배 미만이면 시작하지 않는다.

8.4 이벤트 순서와 재실행

event_id·command_id로 중복을 제거하며 종료된 interaction_id의 UPDATE는 버린다. 최근 종료 ID는 60초간 보관하고, 활성 세션 ID는 종료 전 삭제하지 않는다. 단발 이벤트는 자세 해제와 실행 후 대기 시간 모두 충족한 뒤 재발행한다.

250ms보다 오래된 일반 이벤트는 버리되 END·CANCEL·입력 해제는 나이만으로 버리지 않는다. 오래된 중단 요청도 보수적으로 입력을 해제하고 WAITING으로 처리할 수 있으나, 오래된 브이 이벤트로 자동 활성화하지 않는다.

최신 좌표 UPDATE는 같은 interaction_id와 command_type 안에서 병합한다. 스크롤 같은 상대 변화량은 합산하며, 초당 실행 상한을 초과한 잔여량을 오래 쌓아두지 않고 종료 시 폐기한다. 슬롯 호출 순서에만 의존하지 않고 실행 직전 맥락 버전과 조작 ID를 검사한다.

9 좌표 변환과 화면 처리

9.1 공통 좌표 변환

원본 영상 좌표 u,v를 입력받아 화면 제어 좌표를 만들 때 u'=1-u로 좌우 반전한다. 미리보기만 반전해 표시하며 인식 입력과 저장된 원본 좌표는 반전하지 않는다. 이미 화면 제어 좌표로 변환한 값에 추가 반전을 적용하지 않는다.

조작 영역 bounds는 좌우 반전 후 사용자 미리보기 기준 정규화 좌표다. 초기값은 x=0.100.90, y=0.100.90이다. a=clamp((u'-x_min)/(x_max-x_min),0,1), b=clamp((v-y_min)/(y_max-y_min),0,1)로 변환한다. 비대칭 bounds에도 같은 사용자 기준을 적용한다. 각 축에서 0≤min<max≤1 및 max-min≥0.30을 만족해야 한다. 실제 모니터 크기가 W×H이면 화면 기준점은 round(a×(W-1)), round(b×(H-1))이다. 실제 마우스 명령은 그 결과를 x=clamp(x,2,W-3), y=clamp(y,2,H-3)으로 다시 제한한다. 이 2 실제 픽셀 여백은 커서·클릭·드래그·우클릭 위치에만 적용하고 캡처 영역에는 적용하지 않는다. 조작 영역은 설정에서 조정할 수 있지만 모드별로 다른 값을 몰래 적용하지 않는다.

카메라 프레임 자세·집기 거리 판정은 영상 픽셀 좌표에서 수행하고, 실제 커서·UI 위치 매핑은 위 변환을 사용한다. 제스처 판정 거리와 화면 이동 거리를 혼용하지 않는다.

9.2 UI와 화면 배율

UI 위젯 내부 객체 조작은 해당 캔버스의 논리 너비·높이에 a,b를 곱해 계산한다. 실제 모니터 포인터가 위젯 내부에 있다는 이유만으로 같은 값을 다시 UI로 변환해 쓰지 않는다. 캔버스 좌표와 운영체제 커서 경로는 명령 타입으로 구분한다.

논리 좌표와 실제 픽셀 좌표의 변환은 모니터 배율과 위젯의 전역 위치를 함께 사용한다. 배율을 코드에 1.0으로 고정하지 않는다. DPI 인식 설정은 창 생성 전에 적용하고, UI가 보고하는 배율과 캡처 이미지 크기로 일치 여부를 확인한다. 구체적인 Windows API 및 Qt 호출은 고정한 개발환경에서 담당자가 검증한다.

캡처 좌표는 실제 픽셀 영역으로 먼저 저장하고 UI에서는 이를 논리 좌표로 변환해 표시한다. 캡처 대상 단일 모니터가 변경되거나 화면 해상도·배율이 바뀌면 진행 중 좌표 조작을 종료하고 좌표 변환을 다시 초기화한다. 선택 중 캡처는 취소하고 재선택을 안내한다.

9.3 경계와 흔들림

커서는 9.1의 2 실제 픽셀 내부 범위로 제한하여 자동 이동이 PyAutoGUI 모서리 페일세이프를 유발하지 않도록 한다. 모든 컴퓨터 제어 명령의 최종 경계에서도 같은 제한을 검사한다. 화면 가장자리 2픽셀은 손동작 커서로 직접 지정하지 못하는 제한으로 안내한다. 캡처 영역은 화면 전체 경계를 계속 사용할 수 있다. UI 객체는 최소 32 논리 픽셀 영역이 캔버스 안에 남도록 제한한다. 포인터는 캔버스 경계 안에서만 표시한다. 이미지 확대 배율은 6.3의 범위를 적용한다.

캡처 경계는 두 점의 최소·최대값에서 왼쪽·위는 floor, 오른쪽·아래는 ceil로 계산한 뒤 [0,W]와 [0,H] 안으로 제한한다. width=right-left, height=bottom-top으로 계산하고 최소 32픽셀 조건을 검사한다. 다른 좌표 변환으로 인해 동일 영역에 두 번 반올림하지 않는다.

손을 가만히 둘 때 발생하는 작은 이동에는 2 논리 픽셀 상당의 정지 구간을 적용한다. SCREEN_PIXEL 좌표와 비교할 때는 9.4의 배율 변환 후 실제 픽셀로 비교한다. 마지막 출력 위치와 비교하여 기준을 넘으면 이동을 반영하므로 느린 이동이 영구히 무시되지 않도록 한다.

9.4 방향 의미와 거리 단위

인식 모듈의 SWIPE.direction은 CAMERA_NORMALIZED 기준으로 x 증가=RIGHT, x 감소=LEFT다. 공통 제어가 common/coordinates.py의 변환 함수를 호출하여 수평 반전 설정에 따라 사용자 방향으로 한 번 변환한다. 기본 반전 설정에서는 원본 RIGHT가 사용자 LEFT, 원본 LEFT가 사용자 RIGHT다. 변환된 사용자 방향으로 6.2의 이전·다음 명령을 결정한다. 위치 변환의 u'=1-u와 방향 라벨 교환은 같은 정책의 서로 다른 데이터 적용이며, 이미 변환된 direction을 실행 모듈에서 다시 바꾸지 않는다.

쓸기 거리·직선성·원 경로는 원본 좌표에서 계산한다. 수평 반전은 이동량의 크기와 직선성을 바꾸지 않는다. 세로 delta_y는 원본 영상에서 아래 방향이 양수이며 수평 반전의 영향을 받지 않는다. SCROLL.steps는 위쪽이 양수이므로 공통 제어에서 steps의 부호를 delta_y와 반대로 변환한다.

정지 구간 2와 드래그 시작 거리 6은 논리 픽셀 상당값이다. 실제 출력 좌표 차이가 dx_px, dy_px이고 배율이 sx, sy이면 논리 거리 d=sqrt((dx_px/sx)^2+(dy_px/sy)^2)로 비교한다. 균일 150% 배율에서는 각각 3 실제 픽셀과 9 실제 픽셀에 해당한다. UI_LOGICAL 좌표는 추가 배율 적용 없이 직접 비교한다. 페일세이프 회피의 2픽셀 여백과 캡처 최소 크기 32픽셀은 실제 픽셀 기준이므로 배율을 곱하지 않는다.

10 캡처 기능 상세 처리

10.1 화면 구성과 선택

캡처 화면은 대상 모니터 전체를 덮는 선택 UI, 사각형 테두리, 현재 크기 표시, 저장·취소 버튼으로 구성한다. 선택 화면은 일반 입력을 받으며 뒤쪽 창으로 클릭을 통과시키지 않는다. 저장·취소 버튼은 선택 영역 밖에 배치할 수 있으면 밖에 표시하고, 공간이 없으면 영역 안에 표시하되 촬영 전 모두 숨긴다.

집기 두 점으로 영역을 만들고 집기를 해제하면 READY로 고정한다. READY에서 새 양손 집기를 시작하면 SELECTING으로 돌아가 현재 두 점으로 다시 조절한다. 손 개수 감소로 선택 영역을 지우거나 프로그램을 대기 상태로 변경하지 않는다.

ERROR에서 사용자가 영역을 다시 조절하면 기존 오류를 지우고 SELECTING으로 전환한다. 재시도 버튼은 보존된 유효 영역으로 새 촬영을 시작한다.

10.2 저장 요청의 단일 처리

capture_request_id는 캡처 진입부터 종료까지 유지하고, 각 저장 시도는 별도 command_id를 사용한다. 저장 버튼 연타는 SAVING 진입 시 차단한다. 촬영·파일 저장 담당은 한 번에 하나의 캡처 작업만 실행한다.

현재 오버레이 숨김 알림은 UI 가시성 변경 완료를 뜻하며 실제 화면 합성 완료를 보장하지 않는다. 따라서 숨김 알림 직후 같은 호출 안에서 촬영하지 않는다. 다음 UI 이벤트 루프 이후 100ms의 초기 반영 대기를 적용한 뒤 촬영한다. 100ms는 화면 합성 완료의 보장이 아니므로 Windows 검증에서 오버레이가 포함되는지 반드시 확인하고 설정값을 조정한다. 메인 스레드를 sleep으로 막지 않고 타이머와 완료 신호를 사용한다. 숨김 완료 신호가 1초 안에 오지 않으면 촬영하지 않고 오류로 처리한다.

BROWSER에서 캡처 버튼을 사용할 수 있도록 제어 패널을 표시하되, Chrome 입력이 필요할 때 패널이 포커스를 계속 빼앗지 않게 한다. 캡처 진입 시 자체 제어 패널의 표시 상태를 기록하고 숨긴 뒤 선택 오버레이를 띄운다. 촬영 완료·취소 후 패널 표시 상태를 복구한다.

촬영 순간의 화면을 저장한다. 캡처 진입 순간을 고정한 이미지에서 잘라내는 방식은 사용하지 않는다. 재시도 시에도 화면 내용이 달라질 수 있음을 UI에 표시한다. 캡처 과정의 자체 오버레이와 제어 UI는 숨기되, 뒤에 있는 다른 프로그램 창의 내용은 촬영 순간 그대로 포함한다.

10.3 파일 저장 정책

기본 저장 위치는 운영체제의 사용자 사진 폴더 아래 GestureCapture로 정하고, UI에서 변경할 수 있게 한다. 소스 코드 위치나 실행 파일 설치 폴더를 기본 저장 위치로 쓰지 않는다. 폴더가 없으면 생성하고 권한·저장 실패를 결과로 보고한다.

파일명은 capture_YYYYMMDD_HHMMSS_mmm_순번.png 형식으로 로컬 시각을 사용한다. 이 시각은 파일명에만 사용하고 인식 타이밍에는 사용하지 않는다. 기존 파일을 덮어쓰지 않으며 충돌 시 순번을 증가시킨다.

같은 저장 폴더에 임시 파일을 작성한 뒤 PNG 저장 완료를 확인하고 최종 파일명으로 전환한다. 실패 시 해당 시도에서 만든 임시 파일만 정리한다. 성공 결과에는 saved_path, width, height, capture_request_id를 포함한다. output_path는 사용자가 선택한 저장 폴더 안에서 프로그램이 생성한다.

10.4 중단과 결과 수명

숫자 3, 물리 Esc 또는 종료 요청이 들어오면 실행 전 저장은 취소한다. 이미 촬영·저장이 시작된 작업에는 취소 플래그를 기록하되 파일 성공 여부를 결과로 확정한다. 중단 후 결과를 받아도 재활성화하지 않는다.

저장 5초 경과 시 진행 지연을 표시하고 중복 재시도를 차단한다. 10초를 넘겨도 종료되지 않으면 캡처 작업 오류로 보고 WAITING을 유지한다. 기존 작업이 실제 종료되기 전에는 새 저장 작업을 시작하지 않으며, 늦게 완료된 파일의 경로도 안내한다.

11.2 입력 해제와 비상 중단

컴퓨터 제어 모듈은 프로그램이 누른 버튼과 키를 별도 집합으로 기록한다. 누름 성공 후 등록하고 해제 성공 후 제거한다. RELEASE_ALL_INPUTS는 반복 호출해도 안전하게 동작하며, 프로그램이 누르지 않은 물리 입력을 의도적으로 해제하지 않는다.

프로그램 창과 캡처 화면의 물리 Esc는 전체 조작 중단으로 처리한다. 창에 포커스가 없을 때도 Esc가 동작한다고 보장하지 않으며 초기 버전은 전역 키 후킹을 필수로 두지 않는다. UI에 중단 버튼을 항상 표시한다. 키 이름→가상 키·extended 플래그의 공통 매핑은 computer/keymap.py에 정의하고 일반 입력과 비상 해제가 함께 사용한다. 초기 허용 키는 ctrl, shift, alt, tab, left, right, r, d, t, add, subtract이며 Windows VK는 각각 0x11, 0x10, 0x12, 0x09, 0x25, 0x27, 0x52, 0x44, 0x54, 0x6B, 0x6D다. left/right에는 extended 플래그를 기록하고 비상 해제는 KEYUP을 추가한다. 마우스 버튼은 별도 LEFTUP/RIGHTUP 플래그를 사용한다. 미등록 키는 누르기 전에 거절한다. 확대는 ctrl+add, 축소는 ctrl+subtract 조합을 검증하여 사용한다.

입력 라이브러리의 기본 비상 정지 기능을 임의로 비활성화하지 않고 발생 시 WAITING으로 전환한다. 페일세이프 발생 시 일반 명령 큐를 비우고 WAITING으로 전환한다. PyAutoGUI의 해제 호출도 같은 예외를 낼 수 있으므로 computer/native_release.py에서 ctypes 기반 Windows SendInput으로 프로그램이 누른 버튼·키의 UP 이벤트만 전송한다. 이 경로에서는 커서 이동·새 버튼 누름·클릭을 하지 않으며 FAILSAFE를 일시적으로 끄지도 않는다. 전송 개수가 요청 개수와 일치하는지 확인하고 실패하면 입력 해제 실패로 보고한다. SendInput은 권한 수준 제약을 받으므로 상승 권한 앱 제어는 초기 지원 범위에서 제외하고 일반 권한 환경에서 검증한다. ComputerExecutor가 WAITING에서도 50ms 주기로 커서 위치를 조회하고 정확한 네 모서리 픽셀 (0,0), (W-1,0), (0,H-1), (W-1,H-1) 중 하나이면 BLOCKED_CORNER, 조회 성공한 그 외 위치이면 CLEAR로 CursorSafetyState를 보고한다. 조회 실패는 UNKNOWN이다. 자동 이동의 2픽셀 여백 밖이라는 이유만으로 BLOCKED_CORNER로 분류하지 않는다. Controller는 AppState.cursor_safety에 최신 사본을 보관한다. BLOCKED_CORNER·UNKNOWN 또는 마지막 확인 후 200ms 초과이면 브이 활성화를 거절하고 안내한다. 물리 마우스로 안쪽에 이동해 CLEAR가 확인돼야 새 브이 요청을 수락한다. 경계 감시 자체는 마우스를 움직이지 않는다.

정상 입력 실행 모듈 초기화 시 pyautogui.FAILSAFE=True, pyautogui.PAUSE=0.0을 한 번 설정한다. 커서 moveTo는 duration=0으로 호출하고 드래그는 기존 mouseDown→moveTo→mouseUp 구조를 사용한다. 호출 후 기본 sleep에 의존하지 않으며 커서 출력은 최대 60Hz로 제한하고 최신 좌표를 병합한다. 단축키·스크롤은 각 명령의 간격 정책을 따르고 대기는 작업 타이머로 구현한다. 이 설정은 12.3의 지연 목표를 보장하지 않으므로 실제 호출 소요 시간까지 측정한다. 11.3 정상 종료와 작업 감시

종료 요청 시 명령 접수를 차단하고 context_version을 올린 뒤 입력 해제를 먼저 수행한다. 인식 작업을 중지하고 카메라를 해제하며, 실행 중 저장은 완료 여부를 최대 5초 기다린다. 대기 중 저장은 취소한다. 종료를 기다리는 동안 UI에 상태를 표시하고 이벤트 처리를 유지한다.

작업 스레드가 응답하지 않을 때 강제로 안전하게 끝났다고 표시하지 않는다. 입력 해제 확인, 저장 결과 불명 여부를 로그에 남긴다. 주기적으로 작업의 마지막 응답 시각을 검사해 1초 이상 영상 갱신이 없으면 카메라 오류 경로를 실행한다.

11.4 로그와 공통 설정

재생용 기록은 12.7의 JSONL 픽스처 계약을 사용하고 일반 성능 로그와 별도로 관리한다. fixture 기록 옵션을 켠 경우 설정 사본·입력·시간 기준을 함께 저장한다.

로그는 날짜별 파일로 저장하며 시각, 모듈, 이벤트·명령·조작 ID, context_version, 전환 전후 상태, 결과·오류 코드, 처리 지연을 포함한다. 매 프레임 전체 좌표와 영상을 기본 저장하지 않는다. 성능 측정 모드에서 필요한 좌표와 시각만 기록하고 원본 영상 기록은 별도 옵션으로 둔다.

설정 형식은 JSON으로 고정하고 config/default.json에 사용자 설정 변경분을 합쳐 하나의 AppConfig로 읽는다. 읽기·검증은 src/gesture_control/common/config.py가 담당하며 사용자 경로와 우선순위는 13.3을 따른다. 인식 임계값, 조작 영역, 저장 경로, 감도, 장치 ID, 로그 수준을 포함한다. 숫자 범위를 검증하고 잘못된 값이면 오류를 표시한다. 실행 중 임계값 변경은 진행 중 조작을 종료한 뒤 적용하고 변경 이력을 남긴다. 테스트 결과에는 설정 버전과 소스 코드 버전을 함께 기록한다.

11.5 종료 상한과 미정리 작업

종료 요청을 처음 수락한 단조 시각을 기준으로 전체 상한 10초를 설정한다. 중복 종료 요청이 들어와도 기한을 연장하지 않는다. app_phase는 SHUTTING_DOWN으로 바꾸고 SHUTTING_DOWN 차단 사유를 추가하며, 일반 명령·신규 작업을 더 이상 받지 않는다.

입력 해제를 최우선으로 요청하고 카메라·작업 정리를 진행한다. 저장 완료를 기다리는 5초는 전체 10초 안에 포함된다. 5초가 지나면 대기 중인 저장은 취소하고 진행 중인 작업에는 종료 플래그를 전달한다. 이미 블로킹된 MSS·파일 쓰기를 스레드 종료 요청만으로 중단할 수 있다고 가정하지 않는다.

10초가 지나도 작업 종료 확인이 없으면 SHUTDOWN_TIMEOUT과 미종료 스레드, 입력 해제 확인 여부, 진행 중 저장 ID·경로·결과 불명을 기록한다. app.py의 독립 종료 감시 타이머가 최종 강제 프로세스 종료를 수행하도록 구성하고 비정상 종료 코드는 2로 정한다. QThread.terminate를 이용해 실행 중인 개별 작업만 강제로 끝낸 뒤 정상 상태로 계속 실행하지 않는다. 로그 기록·flush는 제한된 최선 시도로 수행하며 기록 실패 때문에 종료 기한을 무한 연장하지 않는다.

종료 감시는 메인 이벤트 루프와 별도로 동작하는 작은 watchdog을 사용한다. 이는 4개 상시 작업 스레드와 별개의 종료 감시 보조 실행이며, Python 실행 자체가 막히는 네이티브 교착까지 10초 안에 끝낸다고 보장하지 않는다. 해당 경우 Windows의 외부 프로세스 종료가 필요할 수 있음을 시험 결과에 기록한다. 강제 프로세스 종료는 버튼 해제 성공이나 PNG 완성을 보장하지 않는다. 결과 불명 파일을 다음 실행에서 자동 성공으로 표시하지 않는다.

DEV_SIMULATED·REPLAY 시험에서는 ForceExit 어댑터를 Fake로 바꾸어 종료 코드·시각을 수집하고 테스트 프로세스를 종료하지 않는다. 실제 비정상 종료 시험은 별도 자식 프로세스로 수행한다.

12.1 검증 환경과 결과 기록

최종 검증은 Windows 11, 단일 모니터, Windows용 Chrome에서 수행한다. Python·라이브러리·모델 파일 버전, CPU·GPU·메모리, 카메라 해상도·FPS, 모니터 해상도·배율, 조명과 대략적인 손 거리를 기록한다. 초기 카메라 목표는 640×480, 30FPS이며 실제 처리 성능과 별도로 기록한다. 패키지 버전은 설치 및 기본 실행을 확인한 조합을 고정하고 추정 버전을 명세에 기입하지 않는다.

12.7 재생 가능한 픽스처 형식

성능 로그와 재생 입력은 목적을 구분한다. 기본 운영 로그는 11.4를 따르고, 명시적으로 fixture 기록 모드를 켰을 때만 입력 경계의 데이터를 JSONL로 저장한다. 한 줄에 하나의 UTF-8 JSON 객체를 기록하며 NaN·Infinity는 허용하지 않는다. 이미지 원본을 필수로 저장하지 않는다.

픽스처 종류는 LANDMARKS와 CONTROL 두 가지다. LANDMARKS는 특징 계산 이전의 TrackingFrame과 인식 맥락 변경을 기록하여 특징·제스처 판정을 검증한다. CONTROL은 GestureEvent, UIRequest, 실행 결과, InputState, 환경 알림 등 공통 제어 입력을 기록하여 상태·명령을 검증한다. 손 좌표 재생은 카메라와 MediaPipe 모델 자체의 정확도를 검증하지 않는다.

픽스처 디렉터리는 tests/fixtures/<fixture_id>/이며 다음 파일을 포함한다.

manifest.json          # 버전·환경·시드·초기 상태·종료 시각
config.json            # 재현에 필요한 전체 유효 설정 사본
inputs.jsonl           # 시각·순서가 지정된 입력
expected.json          # 검토된 기대 출력과 허용 오차
README.md              # 출처·재현 목적·알려진 제한

manifest의 필수 필드는 fixture_format_version: 1, message_schema_version: 3, fixture_id: str, fixture_kind: LANDMARKS/CONTROL, config_revision: str, config_sha256: str, source_commit: str, random_seed: int, initial_state: AppState 상당 JSON(필수 수명주기 필드를 포함하고 execution_mode=REPLAY), end_at_ms: int, environment: object다. environment에는 손 좌표 입력의 영상 크기·모델 버전·모델 해시·반전 여부와 제어 입력의 모니터 크기·배율을 포함한다. 합성 입력은 source_commit과 README에 생성 방법을 기록하고 실제 촬영이라고 표시하지 않는다.

입력 행 필드는 seq: int, at_ms: int, channel: str, message_type: str, payload: object다. seq는 0부터 연속 증가하고 at_ms는 0 이상의 상대 밀리초이며 비감소 순서다. 동일 시각에서는 seq 순서대로 처리한다. payload의 모든 단조 시각은 기록 시작 시각을 뺀 상대값으로 통일한다. 입력 도착 at_ms와 payload의 촬영 시각은 별개이므로 지연·오래된 이벤트 시험에서는 서로 다를 수 있다.

fixture_kind 허용 channel과 message_type
LANDMARKS tracking: TrackingFrame, context: RecognitionContext
CONTROL gesture: GestureEvent, ui: UIRequest, result: ExecutionResult, input_state: InputState, cursor_safety: CursorSafetyState, system: SystemEvent, overlay: CaptureOverlayHidden, reconnect: CameraReconnectResult

실제 경계에서 사용한 hand_id·interaction_id·request_id는 기록 전체에서 일관되게 유지한다. 개인정보가 포함된 경로는 기록 전에 시험 전용 가상 경로로 교체하고 expected에도 동일하게 적용한다. 프레임 누락은 시간을 건너뛴 것으로 기록하고, 손 없음은 hands=[]인 TrackingFrame으로 명시한다. UNKNOWN 좌우 라벨을 임의로 LEFT/RIGHT로 보정하지 않는다.

{"seq":0,"at_ms":100,"channel":"ui","message_type":"UIRequest","payload":{"schema_version":3,"request_id":"request_1","emitted_at_ms":100,"request_type":"REQUEST_STOP","payload":{}}}

12.8 주입 도구와 가상 시계

재생 도구는 tools/replay_fixture.py, 기록기는 src/gesture_control/common/recording.py에 둔다. 스키마 읽기·검증·재생 엔진은 tests/replay/에 구성하고 tests 패키지에는 init.py를 둔다. 도구는 저장소 개발환경에서 실행하며 사용자 배포본에 필수 포함하지 않는다.

python tools/replay_fixture.py tests/fixtures/stop_during_drag --output work/replay/stop_during_drag
pytest tests/unit tests/integration tests/replay

종료 코드는 0=검증 통과, 1=기대 결과 불일치, 2=형식·설정·실행 환경 오류다. 결과 디렉터리에 actual.jsonl, comparison.json, summary.md를 생성한다. 도구는 expected.json을 덮어쓰지 않는다. 기대값 갱신은 별도 수동 편집·리뷰로 수행한다.

common/clock.py에 Clock.now_ms() -> int 계약을 두고 ProductionClock과 FakeClock을 구현한다. 유지 시간·유실·대기·타임아웃을 계산하는 모듈은 주입받은 Clock만 사용한다. Scheduler.call_at(deadline_ms: int, callback: Callable[[], None]) -> str 및 cancel(timer_id: str) -> None 계약도 주입한다. 운영 구현은 Qt 타이머로 기한에 이벤트를 전달하며, 재생 구현은 가상 시각을 진행시켜 실행한다. 직접 time.sleep을 호출하는 동작 판정 로직은 두지 않는다.

재생 엔진은 다음 입력과 다음 타이머 기한 중 이른 시각으로 이동한다. 같은 시각이면 먼저 기한 타이머를 등록 순서로 실행한 뒤 입력을 seq 순서로 처리한다. 각 단계가 만든 즉시 작업을 FIFO로 소진하고, 실행 종료는 manifest.end_at_ms까지 진행한다. 마지막 입력 직후 종료하여 손 유실·타임아웃을 놓치지 않는다. 실제 Qt 스케줄링 지터는 이 결정적 순서로 검증되지 않으므로 별도 실기 시험에서 경계 전후를 확인한다.

LANDMARKS는 실제 features·recognizer를 호출하고 GestureEvent를 수집한다. CONTROL은 실제 상태 전환·충돌 로직을 호출하고 UI·컴퓨터·캡처 실행부는 명령을 기록하는 Fake로 교체한다. 실행 결과와 CursorSafetyState는 inputs.jsonl에 지정한 시각과 내용으로만 주입하며 Fake가 성공 결과나 주기적인 CLEAR를 자동 생성하지 않는다. 활성화 판정 직전 200ms 이내의 CLEAR 행과 초기 InputState를 픽스처에 명시한다. 50ms 행을 항상 강제하지 않지만 감시 주기·오래된 상태 시험에서는 필요한 관측을 기록한다. observed_at_ms 역시 픽스처 상대 시각이다. initial_state의 CLEAR도 시간이 지나면 만료되며 현재 시각으로 자동 갱신하지 않는다. 이렇게 지연·실패·미응답을 명확히 재현한다.

Clock·Scheduler·ID 생성기는 Controller와 Recognizer 생성자에 키워드 인자로 주입한다. ID 생성 계약은 next_id(prefix: str) -> str이며 재생에서는 고정 시드·순번을 사용한다. 기존 Signal·Slot은 유지한다. 출력 ID를 참조하는 입력 결과는 결정적 ID 규칙에 맞춰 작성한다. 이 계약의 구현 위치와 의존성을 스텁 단계에서 함께 고정한다.

기본 재생은 카메라·PyAutoGUI·MSS·Windows 입력 API를 초기화하지 않는다. 실제 입력을 허용하는 옵션도 두지 않는다. 통합 Fake와 실제 Windows 시험을 별도 실행 경로로 유지한다.

12.9 기대 결과와 회귀 검증

expected.json은 fixture_format_version, output_rules, final_state, forbidden_outputs를 포함한다. output_rules는 순서대로 비교할 출력의 channel, message_type, payload_subset, time_range_ms, numeric_tolerances를 갖는다. 기본 비교는 명령·상태·제스처·결과의 종류와 순서가 정확히 일치해야 하며 좌표·시간에만 명시한 오차를 허용한다.

자동 생성 ID만 정규화할 경우 최초 등장 순서의 일대일 대응을 만들고 이후 참조의 일치까지 확인한다. 단순히 모든 ID 필드를 비교에서 삭제하지 않는다. 시간 허용 범위가 없으면 가상 시각은 정확히 비교한다. 명시하지 않은 추가 클릭·드래그 시작·저장·모드 변경은 실패로 처리한다. 좌표 UPDATE 병합의 차이를 허용하려면 해당 규칙에서만 표본 기준을 선언하며 단발 명령에는 적용하지 않는다.

최종 상태에는 mode, activation, 진행 interaction_id 목록, 입력 해제 상태를 확인한다. forbidden_outputs에는 취소 뒤 SAVE_CAPTURE, 중단 뒤 새 DRAG_START 등 없어야 할 결과를 넣는다. summary에는 최초 불일치 seq·시각·기대값·실제값과 추가·누락 출력을 보고한다.

초기 필수 픽스처는 activate_release, stop_during_drag, two_to_one_hand, scroll_thumb_unknown, scroll_to_stop, capture_hide_timeout, capture_late_result, stale_context, display_change, config_invalid로 구성한다. config_invalid는 메시지 재생 대신 설정 로더 시험 표본으로 분리해 tests/fixtures/config/에 정상·손상·범위 오류 파일을 보관한다.

유지 시간과 타임아웃은 기준값-1ms, 기준값, 기준값+1ms를 각각 검사한다. 설정 초기값이 바뀌면 기존 픽스처의 설정 사본은 보존하고 새 설정용 사례를 추가한다. 기대값은 현재 구현의 출력을 그대로 승인하지 않고 명세상 동작을 기준으로 설계 담당자와 리뷰한다. 원본 로그에서 변환할 때 config 해시·시간 원점·좌표 기준이 빠졌다면 재현 가능하다고 표시하지 않는다.

12.10 추가 시나리오의 상세 조건

Esc는 메인 창·캡처·프로그램이 연 대화상자의 키 이벤트 경로에서 REQUEST_STOP으로 전달한다. 파일 선택 대화상자의 Esc가 단순 닫기로만 소비되지 않도록 공통 처리기를 먼저 적용한다. 포커스가 외부 Chrome에 있으면 프로그램이 전역 Esc를 가로채지 않는 것을 확인한다. 이 경우 중단 버튼·숫자 3·물리 페일세이프 경로를 별도로 시험한다.

해상도·배율 시험은 커서 이동, 실제 드래그, 캡처 SELECTING/READY/SAVING 상태에서 각각 수행한다. 촬영 전에는 오래된 좌표의 캡처를 취소하고, 촬영·저장이 이미 시작되었으면 새 작업을 차단한 뒤 실제 결과를 보고한다. 좌표 맥락 버전을 갱신하고 이전 좌표 명령이 실행되지 않는지 검사한다. 재초기화 실패 시 WAITING 및 일반 입력 차단을 확인한다.

설정 오류는 손상 JSON, 문자열로 된 숫자, 음수 시간, 시작값≥종료값인 집기 비율, 뒤집힌 조작 영역, 모르는 키, failsafe=false를 각각 시험한다. 기본 설정 오류는 시작 차단, 사용자 설정 오류는 원본 보존과 기본값 선택 경로를 검증한다. 쓰기 실패는 임시 파일·최종 교체 실패를 주입해 기존 파일과 메모리 값이 유지되는지 확인한다.

13.3 설정 형식과 경로

설정 형식은 JSON으로 고정한다. 저장소의 config/default.json을 배포 기본값으로 사용하고, 사용자 변경분은 운영체제 사용자 설정 디렉터리의 GestureControl/user.json에 저장한다. Windows 기준 위치는 %LOCALAPPDATA%/GestureControl/user.json이다. macOS 개발 환경은 ~/Library/Application Support/GestureControl/user.json을 사용한다. 사용자 파일이 없으면 기본값으로 실행하며, 실행 파일 폴더에는 사용자 설정을 쓰지 않는다.

실행 순서는 배포 기본값 읽기 → 사용자 변경분을 중첩 객체의 말단 키까지 재귀 병합 → 전체 검증 → AppConfig 생성이다. 알 수 없는 키와 잘못된 자료형·범위는 오류로 표시하고 조용히 무시하지 않는다. 사용자 파일이 손상된 경우 기본값 사용 여부를 UI로 선택하게 하고 원본 파일을 덮어쓰지 않는다. 기본 설정 자체가 잘못되면 일반 입력 기능을 시작하지 않는다.

RecognitionContext는 schema_version: int, context_version: int, mode: Mode, activation: Activation, ready_for_gestures: bool, changed_at_ms: int를 갖는다. 13.5 연결 표와 실행 제약

app.py가 부모 없는 작업 QObject를 생성하고 각각 인식·입력·캡처 QThread에 moveToThread로 배치한 뒤 다음 연결을 한 번만 수행한다. 카메라·MediaPipe·타이머·MSS 등 스레드 소유 자원은 생성자에서 만들지 않고 해당 스레드에서 호출되는 start에서 생성한다. 모듈 간 고정 연결을 생성자 내부에서 중복 수행하지 않는다. 예외로 일회성 ImageLoadSignals.finished → UiBridge.on_images_loaded 연결은 UiBridge가 해당 작업 생성 시 한 번 구성하고 완료 후 정리한다. 이 내부 작업 연결은 app.py의 고정 연결 목록 대상이 아니다.

다른 스레드로 넘어가는 연결은 queued 방식으로 구성한다. 메인 스레드에서 작업 객체의 슬롯 메서드를 직접 호출하여 작업을 실행하지 않는다. start에서 종료되지 않는 while 루프로 작업 스레드 이벤트 루프를 막으면 stop과 set_context가 도착하지 않으므로, 프레임 한 번 처리 후 이벤트 루프로 복귀하는 구조를 사용한다. 장치 읽기 자체의 무기한 대기는 피하고 응답 감시를 둔다.

Signal에는 자동 우선순위가 없다. execute 슬롯은 입력 명령을 내부 큐에 넣고 짧게 반환하며, 한 단계씩 실행하도록 한다. release_inputs는 대기 일반 명령을 무효화하고 해제 작업을 다음 실행 단계의 최우선으로 넣는다. 입력 시퀀스 중간에도 맥락 변경과 종료 플래그를 확인한다. 실행 중인 하나의 OS 호출을 강제로 선점할 수 있다고 가정하지 않는다.

CaptureService는 캡처 스레드의 start에서 MSS 인스턴스를 생성하고 같은 스레드에서만 사용·close한다. 다른 스레드에서 만든 인스턴스를 전달하지 않는다. stop은 대기 작업 취소와 진행 작업 정리 후 자원을 닫고 stopped를 발행한다. ComputerExecutor.stop도 입력 해제 확인·감시 타이머 종료 후 stopped를 발행한다. VisionWorker.stopped는 카메라·모델 정리가 끝난 뒤 발행한다.

ShutdownCoordinator는 메인 스레드 QObject이며 stop 신호와 각 on_*_stopped 무인자 슬롯을 갖는다. 입력 해제 후 각 작업의 stop을 요청하고 정상 경로에서는 모든 QThread.finished를 확인한 뒤 앱을 종료한다. 종료 요청 후 10초의 전체 상한을 넘기면 11.5의 비정상 종료 경로를 적용한다. 종료 확인 중 메인 스레드를 wait로 막지 않는다. 작업 객체와 스레드 참조는 finished까지 유지하고 스레드 객체는 그 뒤 deleteLater한다.

캡처는 완료될 때까지 블로킹될 수 있으므로 실행 직전 맥락 확인을 수행하고, 시작 이후 중단은 5.9의 결과 처리 규칙을 따른다. 모드 전환을 큐에 넣었다는 이유만으로 이미 실행한 저장이 취소되었다고 판정하지 않는다.

13.7 Windows 활성 창과 배포 계약

활성 창 확인은 computer/foreground.py에서 Python 표준 라이브러리 ctypes로 구현한다. GetForegroundWindow → GetWindowThreadProcessId → OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION) → QueryFullProcessImageNameW 순서로 실행 파일 경로를 얻고, 파일명이 대소문자 무관하게 chrome.exe인지 검사한다. 열린 프로세스 핸들은 반드시 CloseHandle로 정리하며 64비트 포인터 타입과 함수 인자·반환 타입을 명시한다. 초기 버전에는 pywin32와 psutil을 추가하지 않는다. Windows 프로세스 경로 조회

제목 문자열에 Chrome이 포함되는지만으로 허용하지 않는다. 창 없음·조회 실패·접근 거절은 판정 불가로 처리해 브라우저 명령을 차단한다. 공개 함수는 get_foreground_process_path() -> str | None, is_chrome_foreground() -> bool로 정의한다. 실행 직전 재검사하되 확인과 입력 사이에 창이 바뀔 수 있는 한계가 있으므로 단축키를 짧은 시퀀스로 실행하고 변경 감지 시 남은 시퀀스를 취소·해제한다. 원자적인 특정 창 입력을 보장한다고 문서화하지 않는다. macOS에서는 Windows API를 초기화하지 않고 DEV_SIMULATED 실행 모드로 개발한다. 아래 13.10의 모의 어댑터와 REPLAY 픽스처 규칙을 구분한다.

배포 도구는 PyInstaller로 정하고 Windows에서 Windows용 onedir 배포본을 빌드한다. requirements-dev.txt에 검증한 PyInstaller 버전을 고정한다. packaging/launcher.py는 gesture_control.app.main을 호출하며 packaging/gesture_control.spec의 pathex에 저장소 src를 포함한다. spec의 datas에 config/default.json과 assets/models/hand_landmarker.task를 각각 동일한 상대 디렉터리로 포함한다. spec 경로는 저장소 루트를 기준으로 안정적으로 해석하고 build 명령은 pyinstaller --clean packaging/gesture_control.spec로 통일한다. PyInstaller 데이터 파일 포함 안내

리소스 루트는 개발 시 저장소 루트, frozen 실행 시 PyInstaller 번들 루트를 사용하도록 app.py의 단일 함수로 해석한다. 모델과 기본 설정을 현재 작업 디렉터리나 사용자 설정 폴더에서 우연히 찾는 방식은 사용하지 않는다. 쓰기 가능한 사용자 설정·로그·캡처 위치는 번들 밖에 유지한다.

Qt 플러그인, MediaPipe 네이티브 라이브러리와 추가 데이터는 고정 버전의 빌드 훅으로 수집되는지 확인한다. 부족한 항목은 spec 또는 프로젝트 훅에 명시하고 이유를 기록한다. .task만 포함했다고 배포가 완료된 것으로 보지 않는다. Python이 설치되지 않은 Windows 시험 환경에서 네트워크 없이 시작·양손 추적·입력·캡처를 검증하며, 임의 작업 디렉터리 및 한글·공백 경로에서도 실행한다. 모델 버전·SHA-256·설정 revision과 의존성 목록을 배포 결과에 기록한다.

13.8 이미지 작업과 공통 좌표 구현

ui/image_loader.py의 ImageLoadJob은 QRunnable로 구현하고 UiBridge가 소유한 전용 QThreadPool(maxThreadCount=1)에 제출한다. 작업은 command_id·context_version·불러오기 세대 번호를 받아 QImage와 파일별 오류를 만든다. ImageLoadSignals.finished(object)는 메인 스레드 UiBridge.on_images_loaded(result: ImageLoadResult)로 queued 연결한다. ImageLoadResult는 command_id, context_version, generation, images: tuple[DecodedImage,...], rejected_files이며 DecodedImage는 path와 QImage를 갖는 UI 내부 자료형이다. 이 QImage 자료형은 common으로 전파하지 않는다.

UiBridge는 현재 요청·세대와 일치할 때만 QPixmap으로 변환·반영하고 일반 ExecutionResult를 발행한다. 취소·모드 변경으로 오래된 결과가 되면 폐기한다. 종료 시 새 작업 제출을 차단하고 완료를 비동기로 확인한다. QThreadPool 작업에서 QWidget·QPixmap을 사용하지 않는 것을 리뷰한다.

common/coordinates.py에는 순수 변환 함수 map_camera_point, camera_direction_to_user, screen_rect_to_ui, ui_rect_to_screen, logical_distance를 둔다. Qt·Controller·창 객체에 의존하지 않으며 변환에 필요한 원점·배율은 명시적 인자로 받는다. CoordinateTransform은 monitor_id, width_px, height_px, scale_x, scale_y, widget_origin_px_x, widget_origin_px_y를 가진 공통 자료형이다. UI는 현재 창의 기하 정보로 이를 만들고 common 함수를 통해 캡처 픽셀을 논리 좌표로 표시한다. control/coordinate_policy.py는 어느 화면·대상·변환 설정을 사용할지만 결정한다. UI가 control을 import하지 않는다.

공개 함수 형태는 screen_rect_to_ui(rect: CaptureRect, transform: CoordinateTransform) -> LogicalRect, ui_rect_to_screen(rect: LogicalRect, transform: CoordinateTransform) -> CaptureRect, logical_distance(dx_px: float, dy_px: float, scale_x: float, scale_y: float) -> float다. LogicalRect는 left, top, width, height의 float와 target_id를 갖는다. map_camera_point(point: Point2D, bounds: ControlBounds, target: TargetGeometry) -> Point2D와 camera_direction_to_user(direction: Direction, mirrored: bool) -> Direction도 동일 모듈에 둔다. ControlBounds는 x_min/x_max/y_min/y_max, TargetGeometry는 space/target_id/width/height/mirrored를 갖는다. 실제 커서 전용 마진 제한은 컴퓨터 제어 경계에서 별도로 적용한다.

13.9 설정 병합과 편집 허용 목록

사용자 JSON은 기본 JSON과 객체 안쪽 말단까지 재귀 병합한다. 예를 들어 gestures.stop_hold_ms 하나만 변경하면 다른 gestures 값은 기본값을 유지한다. 배열이 있으면 배열 전체를 교체하고, null은 해당 필드에서 허용한 명시적 값이며 삭제 연산이 아니다. 객체 자리에 숫자·배열을 넣으면 거절한다. 병합 전 키·자료형, 병합 후 전체 범위와 값 간 관계를 검증한다.

설정 대화상자는 다음 키만 변경할 수 있다: gestures.activate_hold_ms, stop_hold_ms, capture_hold_ms, click_bend_ms, click_release_ms, pinch_enter_ratio, pinch_exit_ratio, smoothing_tau_ms, scroll_step_ratio; coordinates.x_min/x_max/y_min/y_max; capture.overlay_settle_ms; logging.level. gestures 접두사를 생략한 나머지 제스처 항목도 같은 객체의 키다. 시간은 203000ms, pinch 비율은 0.051.0이며 enter<exit, scroll_step_ratio는 0.010.20, bounds는 사용자 미리보기 기준으로 0≤min<max≤1 및 각 축 max-min≥0.30, overlay 대기는 01000ms로 제한한다. scroll_step_ratio 초기값은 0.04로 설정 파일에 추가한다.

저장 폴더는 REQUEST_SET_SAVE_DIR 경로에서만 변경한다. 카메라 장치·해상도, 모델 경로, running_mode, num_hands, 신뢰도, handedness_swap, fail-safe, 마진, 실행 빈도, schema/config 버전은 일반 설정 대화상자에서 변경하지 않는다. 개발용 파일 수정은 허용하지만 재시작과 검증을 요구한다. 사용자 파일에는 변경분만 저장하고 전체 유효 설정 사본은 시험 결과에 별도로 기록한다.

13.10 실제 실행과 모의 개발 및 재생

WINDOWS_REAL은 실제 Windows 장치·입력을 사용하는 기본 배포 모드다. DEV_SIMULATED는 Windows 외 개발환경의 기본 모드이며 UI에 모의 실행이라고 항상 표시한다. 인식 실험을 위해 실제 카메라를 사용할 수 있지만 컴퓨터 제어·캡처는 Fake 어댑터로 연결하고 실제 OS 입력·화면 촬영은 수행하지 않는다. 모의 캡처는 시험용 이미지와 출력 경로를 사용한다.

DEV_SIMULATED의 FakeComputerExecutor는 50ms마다 가상 중앙 위치의 CLEAR를 현재 Clock 시각으로 보고하고, 초기 빈 InputState 및 요청에 대한 모의 결과를 제공한다. 따라서 브이 활성화와 UI·인식 통합 개발이 가능하다. 물리 모서리 감지·실제 드래그·Windows 포커스가 검증된 것으로 보고하지 않는다. 카메라 없이 시작하는 모의 개발은 명시적 합성 프레임 공급자를 선택하고 camera_status=CONNECTED를 모의 공급자 연결 상태로 사용한다.

REPLAY에서는 자동 CLEAR·자동 성공 보고를 전부 끄고 12.7의 기록된 입력만 사용한다. manifest에 실행 모드를 REPLAY로 기록하고 각 CursorSafetyState 시각을 재생한다. DEV_SIMULATED의 편의 동작을 REPLAY에 적용하지 않는다. Windows 외 환경에서 WINDOWS_REAL을 요청하면 시작 오류를 표시하며 조용히 실입력 또는 모의 입력으로 바꾸지 않는다.

설정 revision 1.2는 scroll_step_ratio=0.04와 bounds의 사용자 기준·최소 폭 검증을 포함한다. 이전 사용자 설정은 누락된 scroll_step_ratio를 기본값으로 채우고 전체 검증 후 사용한다. 비대칭 bounds는 이전 의미가 불명확하므로 사용자에게 새 기준을 안내하고 명시적으로 확인받거나 기본 대칭값으로 되돌린다. 기존 파일은 백업한 뒤 성공적으로 저장하며 검증 실패 시 덮어쓰지 않는다.

14 개발 및 협업 규칙

14.1 Git 브랜치와 커밋

main은 설치와 기본 실행이 가능한 통합 브랜치로 유지한다. 별도 장기 develop 브랜치를 만들지 않고 main에서 작업 브랜치를 생성한다. main 직접 push는 사용하지 않으며 가능한 저장소 설정에서 PR 병합을 요구한다.

작업 브랜치 예시
기능 feat/vision-tracking, feat/capture-save
오류 수정 fix/drag-release
문서 docs/interface-contract
구조 개선 refactor/controller-state
도구·환경 chore/dev-tools

커밋 메시지는 type(scope): 요약으로 작성한다. type은 feat, fix, docs, refactor, test, chore를 사용하며 scope는 vision, gesture, control, ui, computer, capture, common, config 등으로 정한다. 예시는 fix(computer): 추적 유실 시 왼쪽 버튼 해제다. 요약에는 실제 변경을 적고 의미 없는 update만 쓰지 않는다.

하나의 PR은 하나의 기능·오류·규격 변경을 중심으로 구성한다. 작업 완료 후 main의 변경을 반영하고 충돌을 해결한다. 다른 사람이 사용하는 브랜치의 이력을 임의로 덮어쓰지 않는다. 병합 방식은 squash merge로 통일하고 병합 후 작업 브랜치를 삭제한다.

14.2 PR과 리뷰

PR에는 변경 목적, 영향을 받는 모듈, 규격·설정 변경 여부, 검증 방법과 결과, 남은 제한을 적는다. UI 변경에는 필요할 때 화면 또는 짧은 시연을 첨부한다. Windows 검증을 수행하지 못했다면 미검증이라고 표시하고 실제 Windows 담당자에게 확인을 요청한다.

작성자 외 최소 1명이 확인한 뒤 병합한다. common/messages.py, enums.py, Signal/Slot, 설정 키, 상태 전환 의미를 바꾸는 PR은 설계 담당자와 영향을 받는 모듈 담당자의 확인을 모두 받는다. 한 사람이 두 역할을 겸하면 같은 사람이 확인할 수 있지만 작성자 본인의 승인만으로 대체하지 않는다.

단순 오탈자 문서는 전체 기능 시험을 요구하지 않는다. 반면 입력 해제, 모드 전환, 명령 순서 또는 좌표 변환 변경은 관련 12번 시나리오의 검증 결과가 있어야 한다. 실패한 시험을 숨기거나 테스트를 삭제해 병합 조건을 맞추지 않는다.

14.3 코드 작성과 검사

PEP 8을 기본으로 하고 포맷·정적 검사는 Ruff, 타입 검사는 mypy, 자동 시험은 pytest로 통일한다. 도구 버전은 최초 실행 확인 후 requirements-dev.txt에 고정한다. pyproject.toml에 줄 길이 100, Ruff 기본 E4·E7·E9·F·I 규칙, mypy의 공통 정의·공개 인터페이스 검사를 설정한다. Python 버전은 검증된 공통 버전과 일치시킨다.

mypy src/gesture_control/common src/gesture_control/control

초기 스텁 단계에는 검사 대상과 시험 파일을 먼저 준비한다. 기능 시험에 실제 입력이 필요하면 기본 자동 시험에서 실행하지 않고 Windows 수동 검증으로 분리한다. 자동 시험의 기본 컴퓨터 제어는 Fake 구현을 사용해 개발자 PC에 실제 클릭을 보내지 않는다.

14.4 의존성 및 파일 관리

가상환경은 저장소 루트의 .venv를 사용하고 Git에 포함하지 않는다. 실행 의존성 변경 시 requirements.txt와 필요하면 pyproject.toml을 함께 수정한다. 플랫폼별 조건이 필요한 의존성은 환경 마커 또는 명확한 설치 절차로 표현하며 macOS에서 설치되지 않는 패키지를 무조건 공통 설치하지 않는다.

.gitignore에는 .venv, pycache, pytest·mypy·Ruff 캐시, build, dist, 로컬 로그, 사용자 설정, 생성 캡처 파일을 포함한다. 큰 모델·시연 영상은 저장소 정책에 맞는 배포 위치를 사용하고 파일명·버전·해시·확보 방법을 README에 기록한다. 모델을 얻을 수 없는 상태로 배포 완료를 선언하지 않는다.

실제 캡처 이미지, 개인 화면 영상, 비밀정보를 시험 표본으로 무심코 커밋하지 않는다. 테스트 표본은 작은 합성 좌표나 공유 가능한 화면을 사용한다. 설정 기본값에는 사용자 이름이 포함된 경로를 넣지 않는다.

14.5 명세 변경과 버전 관리

저장소에서는 docs/architecture.md를 본 명세의 정본으로 사용한다. CHANGELOG.md에는 코드와 명세의 주요 변경을 기록하고 PR에서 서로 연결한다. 메시지 필드·단위·Signal 이름·상태 전환이 달라지면 코드와 문서를 같은 PR에서 수정한다.

문서 버전은 major.minor로 관리한다. 기존 연결을 깨는 규격 변경은 major, 기존 동작 의미를 보존하는 설명 보완·규칙 추가는 minor를 올린다. schema_version은 문서 버전과 별개이며 직렬화 또는 메시지 호환성이 깨질 때 갱신한다. 설정 키 변경에는 config_revision 및 사용자 설정 이전 방법을 함께 기록한다.

변경 절차는 문제·영향 모듈 제시 → 설계 및 관련 구현 담당자 합의 → 공통 정의·스텁·문서 수정 → 송신·수신 모듈 동시 반영 → 관련 시험 → 변경 이력 기록 순서다. 이미 배포한 데이터의 필드를 조용히 다른 의미로 재사용하지 않는다.

초기 임계값 조정도 config_revision과 시험 조건을 기록한다. 사용자와 확정한 동작 의미를 바꾸는 변경은 단순 감도 조정으로 취급하지 않고 별도 설계 변경으로 검토한다.
