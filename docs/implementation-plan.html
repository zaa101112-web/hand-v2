01 / ESTIMATION BASIS

무엇을 하루로 계산했는가

1 MD = 개발자 1명의 실제 작업 8시간. 일정의 D01은 착수일이며 달력 날짜가 아닙니다.

항목계획 기준
기준 문서HAND v2 설계 Baseline 1.0. 특히 명령표, 구조·DI, 상태 규칙, 40개 검증 항목과 결정 기록을 따릅니다.
개발 인력Python·기본 Qt·Git·테스트 작성 경험이 있는 개발자 1명. 설계·구현·리뷰·시험·빌드를 모두 같은 사람이 담당합니다. 두 작업을 같은 날 병렬 담당한 것으로 계산하지 않습니다.
재사용 전제기존 프로토타입은 동작/실패 참고 자료입니다. 검증 가능한 순수 로직의 선택적 재사용은 가능하나 이전 소스를 통째로 이식하거나 이전 테스트 통과를 v2 성과로 재사용하지 않습니다.
작업 시간준비·실패 시험·구현·회귀·리팩터링·작업 기록을 포함한 8시간입니다. 회의·다른 과제·수업 때문에 하루 4시간만 투입하면 같은 작업량에 기본 약 80일, 예비 포함 약 90일이 필요합니다.
범위Windows 11 x64, 단일 모니터, Chrome 단축키, 이미지·발표, 물리 입력 캡처, 연습·설정·복구·배포. 손 좌표 마우스 이동/클릭/드래그/휠, 임의 매크로, 시연 영상은 추가하지 않습니다.
추정의 의미40 MD는 계획 추정이며 40일에 무조건 끝난다는 보장이 아닙니다. D10/D15에서 실측 난이도로 재산정합니다. 기본 일정에 통상적 수정 시간을 넣고, 예비 5 MD는 추가 위험에만 사용합니다.
평가 참여자개발자는 1명이지만 설계의 인식률 평가에는 별도 참여자 3명이 필요합니다. 참여자의 테스트 시간은 개발자 공수에 더하지 않으며, 진행·기록·분석을 하는 개발자 시간은 D35–36에 포함합니다.

일반 개발일의 8시간

0.5h설계 확인1.5hRed3.5hGreen1.5h회귀·정리1h문서·기록

준비·실기 검증일은 점검 기준/환경 1h + 주작업/측정 4h + 분석/재검증 2h + 기록 1h = 8h로 배분합니다. 구현 시간이 늘어났다고 검증 시간을 없애지 않습니다. 당일 수행하지 못한 검증은 이월 공수와 미완료 상태로 기록합니다.

완료 조건은 시간 경과가 아니라 관찰 가능한 결과입니다.

40개의 카드에는 목표·선행 작업·관련 설계·먼저 확인할 실패 조건·구현·검증·산출물을 넣었습니다. 날짜만 지났다고 완료 표시하지 않습니다. 기준 계획은 유지하며 실제 완료/미완료는 진행 기록에 표시합니다. M02의 남은 실기 검증을 완료하기 전 전체 PASS로 처리하지 않습니다.

08 / CHANGE & COMPLETION

일정이 어긋났을 때의 처리

  1. 매일 시작: 설계서와 오늘 카드, 관련 V2-T 기준을 먼저 읽습니다. 문서/기본값 변경이 필요하면 결정 기록과 시험 영향을 함께 갱신합니다.
  2. 막히면: 실제 투입 시간·재현 조건·남은 작업을 적습니다. 선행 실패를 숨기고 다음 의존 작업을 완료로 세지 않습니다. 장비 대기는 MD가 아니라 달력 지연으로 따로 기록합니다.
  3. 오류 분류: 다른 앱 오입력·잔류 키·잘못된 파일 덮어쓰기·반복 크래시는 해당 기능 사용과 후속 게이트를 막습니다. 실패 시험을 먼저 만든 뒤 수정합니다. 경미한 문구/배치 결함은 같은 5MD 블록 내에 배정하되 누락하지 않습니다.
  4. 예비일 사용: B01–B05에서 실제 원인에 맞는 하루를 삽입하고 총 투입량을 갱신합니다. 버퍼를 썼다는 이유로 자동/실기/사람 평가를 생략하지 않습니다.
  5. 중요한 변경만 확인: 범위 축소·지원 환경 변경·데이터 손실 가능 작업·외부 공개는 사용자와 결정합니다. 일상적인 코드 구조·표현·시험 배치는 설계 범위 안에서 자율적으로 진행합니다.
  6. 완료: 모든 필수 게이트에 증거가 있고 코드·설계·계획·배포 hash가 일치할 때만 완료합니다. NOT_RUN을 PASS로 바꾸거나 시연 영상으로 실제 검증을 대신하지 않습니다.
